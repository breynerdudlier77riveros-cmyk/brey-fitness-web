Arquitectura

Las capas del sistema, su bounded context, el flujo completo de un ciclo de uso real, sus dependencias y sus invariantes. Observabilidad/auditoría/eventos se resumen aquí y se detallan en 08 (Seguridad) y 13 (API Interna) — este documento no tiene un módulo dedicado de observabilidad, por diseño explícito del alcance pedido.

Capas

CapaResponsabilidad
PresentaciónPanel del entrenador (privado, autenticado) y vista de reporte público (anónima, de solo lectura) — dos superficies completamente distintas que nunca comparten componente ni endpoint (10)
AplicaciónCasos de uso: CrearCliente, RegistrarMedición, GenerarReporte, CrearEnlacePúblico, etc. (02, 13) — orquestan el dominio, no contienen reglas de negocio propias
DominioEntidades, agregados, value objects, invariantes (02) — el núcleo que no sabe nada de HTTP, base de datos ni UI
InfraestructuraRepositorios concretos, almacenamiento de fotografías, generación de tokens públicos (13, 15)

Bounded context

El BCS es su propio bounded context, separado del bounded context del Core Product (perfil, Motor BPS, Progression Engine). Comparte, como mucho, la noción de "Entrenador" como identidad autenticada — pero el BCS no importa ni depende de ningún modelo de dominio de esos otros sistemas. Un Cliente del BCS es una entidad propia de este contexto: no es lo mismo que un profile de usuario del Core Product, aunque en el futuro puedan vincularse (14, 17).

Flujo end-to-end de un ciclo real

Del alta del cliente al reporte visto por el cliente
sequenceDiagram
  participant E as Entrenador
  participant S as BCS (panel)
  participant D as Dominio
  participant C as Cliente

  S->>D: Cliente nuevo (activo)
  E->>S: registra medición (fecha, valores)
  S->>D: valida + persiste Medición
  E->>S: genera enlace público
  S->>D: crea EnlacePúblico (token aleatorio)
  S-->>E: URL de solo lectura
  E-->>C: comparte el enlace manualmente
  C->>S: abre el enlace (sin login)
  S->>D: resuelve token → Cliente
  D-->>S: historial + reporte generado
  S-->>C: reporte de solo lectura

Dependencias

Depende dePara qué
Identidad del entrenador (autenticación ya existente en BREY)El BCS reutiliza el mecanismo de login del Core Product para el panel — no implementa su propio sistema de cuentas (08)
Almacenamiento de archivosFotografías opcionales por medición (03, 11)

Quién depende del BCS: nadie, en v1 — es una hoja del árbol de dependencias de BREY, no un servicio consumido por otros sistemas.

Invariantes de arquitectura

  • IN-A1: el panel del entrenador y la vista pública nunca comparten el mismo endpoint ni el mismo componente de presentación — están separados por diseño (10).
  • IN-A2: el dominio nunca conoce el token del enlace público — la resolución token→cliente ocurre en la capa de aplicación (13).
  • IN-A3: ninguna capa superior (presentación, aplicación) contiene reglas de validación de variables de composición corporal — esas reglas viven exclusivamente en el dominio (02, 03).
  • IN-A4: toda escritura (crear/editar/eliminar cliente, registrar/corregir medición, generar/revocar enlace) queda auditada — detalle completo en 08.

Observabilidad, auditoría y eventos — resumen

Nota de alcance

El listado de secciones que este handbook debía cubrir pedía documentar "auditoría, observabilidad, eventos" dentro de la arquitectura, pero la tabla de contenidos de 18 módulos que el propio encargo especificó no incluye un módulo dedicado de Observabilidad. Se resuelve así: la auditoría (quién hizo qué y cuándo) se documenta en 08 (Seguridad), junto a permisos y RLS, por ser inseparable de esos controles de acceso. Los eventos de dominio (qué emite cada caso de uso) se documentan en 13 (API Interna), junto a los contratos de los propios casos de uso. Ningún contenido se omite — se ubica donde es más consultable.
