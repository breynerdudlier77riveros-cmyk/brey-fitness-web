Notación REST, transporte agnóstico

API-ADR-01 — resumen (ver 15 para el ADR completo)

El Engineering Handbook (06) afirma: "BREY no expone una API pública versionada — sus contratos internos son las firmas de los repositorios (Queries), las Server Actions (Commands) y los 2 Route Handlers reales." Este documento no lo contradice: cada operación de este catálogo se expresa con ruta lógica + método semántico (ej. POST /bcs/clientes) como notación transporte-agnóstica — exactamente lo que el propio BCS Handbook (13) ya hace con pseudocódigo ("este documento no elige lenguaje ni framework"). Una ruta de este documento se realiza hoy como una Server Action o un Repositorio; mañana, si BREY expone una API pública, la misma ruta se realiza como un Route Handler real — el contrato no cambia, solo su transporte.

REST como vocabulario, no como transporte obligatorio

Los recursos de este catálogo (07) son sustantivos — Cliente, Medición, Workout, Diagnóstico — nunca verbos (nunca POST /crearCliente). Las acciones que no encajan en CRUD puro (revocar un Enlace, archivar un Cliente, cerrar una sesión) se modelan como sub-recursos de acción (POST /bcs/enlaces/{id}/revocar) en vez de forzarlas dentro de un verbo HTTP que no las representa fielmente (04). Solo los Aggregate Roots reales del Domain Model Handbook (08) son recursos con identidad propia direccionable por id — Programa, Bloque, Mesociclo y Microciclo nunca son un recurso GET /programas/{id}, porque no tienen fila propia (Domain Model Handbook, 13): se leen como vista derivada del Usuario que los posiciona.

Stateless

Ninguna operación de este catálogo depende de un estado de sesión de servidor más allá de la identidad autenticada (03). Cada request lleva toda la información que su operación necesita — el servidor nunca "recuerda" un paso anterior de un flujo multi-request salvo lo que ya está persistido (ej. el estado de la máquina de Diagnóstico, 07). La única excepción documentada es la cola local del Workout Player (Architecture Handbook, 09) — y esa cola vive en el cliente, no en el servidor; el servidor solo ve eventos ya resueltos en el momento de la sincronización (11).

Determinismo

Toda operación que invoca un motor (Progression Engine, Recovery Engine) es una función pura sobre sus argumentos explícitos (Progression Engine Handbook, IN-P1) — la misma entrada produce siempre la misma salida. Esto tiene una consecuencia directa de contrato: ninguna entrada implícita. La fecha del ciclo, la versión del catálogo y la ventana de historial siempre son parámetros explícitos de la operación (Motor BPS Handbook, BPS-022) — nunca Date.now() leído dentro del motor. Un endpoint que invoca un motor documenta exactamente qué recibe ese motor, sin dejar nada a la implementación (Engineering Handbook, FT-03).

Idempotencia

Se detalla operación por operación en 11. Como principio: toda operación de creación que pueda repetirse por un reintento de red (activación por compra, generación de semana, sincronización de eventos offline) declara explícitamente su clave de idempotencia o declara explícitamente que no la tiene todavía (Engineering Handbook, FT-04) — nunca se asume idempotencia sin una clave nombrada.

Versionado

No existe hoy un esquema /api/v1/ porque ningún consumidor externo a BREY existe todavía (Engineering Handbook, 06). Este documento adopta la misma postura que el Engineering Handbook: la ausencia de versionado explícito es válida mientras el único consumidor sea el propio frontend de BREY, desplegado atómicamente junto con el backend — pero cualquier contrato nuevo que este documento formaliza debe evolucionar de forma aditiva (10) desde el primer día, para que introducir versionado real, el día que un consumidor externo exista, no requiera reescribir contratos ya publicados.

JSON como único formato

Todo body de request y toda response de este catálogo son JSON — nunca form-urlencoded, nunca XML, nunca multipart salvo el caso explícito de subida de fotografía en Mediciones del BCS (07, BCS-V25), donde el archivo se sube a Storage y solo su referencia (foto_url) viaja en el JSON del resto de la operación (Implementation Handbook, 05).

UTC

Todo timestamp de este catálogo se transmite en UTC, formato ISO-8601 (created_at, fecha, fecha_ciclo). Ninguna operación acepta ni devuelve una fecha con zona horaria implícita del cliente — la conversión a hora local es responsabilidad exclusiva de la capa de presentación, nunca del contrato (consistente con el determinismo de 04-salidas del Motor BPS Handbook, que exige fecha del ciclo como parámetro explícito, nunca ambiguo).

snake_case vs. camelCase

CapaConvenciónOrigen
Nombres de columna / campo persistidosnake_case, sufijo de unidad explícito (peso_kg, altura_cm)Engineering Handbook (05) — convención ya real en las 5 tablas existentes
Body de request / response de este catálogosnake_case — se transmite tal cual sale de la capa de datos, sin una capa de traducción a camelCase en el contratoEste documento — para que un campo tenga un único nombre en toda la cadena (dato → contrato), sin dos alias del mismo concepto

Este documento nunca introduce camelCase en un payload de request/response — evita exactamente el riesgo que el Domain Model Handbook ya advirtió para las 25 variables del BCS (AR-017): dos nombres distintos para el mismo campo, según la capa que lo mire.

Convenciones globales — resumen

PrincipioRegla
SSoT (FT-01)Un campo, un nombre, una capa dueña — nunca dos contratos describen el mismo dato con formas distintas sin que uno cite al otro
Fail Visible (FT-05)Ninguna operación falla en silencio — un repositorio que no encuentra nada devuelve null/[] explícito, nunca una excepción no capturada hacia el llamador
Auditabilidad (P2/P3)Toda mutación de dominio (no de infraestructura) queda registrada — como fila de progression_events en Core Training/Progression/Recovery, o como efecto auditado en BCS (08)
Inmutabilidad de historial (FT-09)Ninguna operación de este catálogo edita en sitio un registro histórico cerrado (WorkoutLog, Medición vigente, EventoProgresión) — la corrección siempre crea un registro nuevo (11)
