Logs

Convención real ya en uso

console.warn(`[contexto] mensaje`) para condiciones degradadas pero no fatales (ej. "[lead] BREVO_API_KEY sin configurar"); console.error(`[contexto] mensaje`) para fallos de un servicio externo. El prefijo [contexto] entre corchetes identifica el origen ([lead], [contacto]) — todo log nuevo sigue este mismo formato para mantenerse buscable.

No hay un logger estructurado (JSON) ni una librería dedicada (Pino, Winston) — futuro, evaluado cuando el volumen de logs justifique búsqueda estructurada sobre grep manual en la plataforma (12).

Tracing

futuro — sin distributed tracing. A la escala actual (sin microservicios, un único proceso Next.js), un trace ID por request añadiría complejidad sin un problema real que resolver todavía.

Errores y Warnings

Distinción ya real en el código: warn = el sistema se degrada mostrando un comportamiento alternativo conocido (formulario responde "disponible pronto" en vez de fallar); error = un servicio externo respondió con un fallo no anticipado. Ningún catch debe quedar vacío (FT-05, Fail Visible) — si no hay nada útil que loguear, es señal de que el catch no debería existir.

Auditoría y Replay

El mecanismo completo de auditoría/replay pertenece a progression_events (07) — especificado, no implementado. Cuando exista, el índice (user_id, created_at desc) ya definido por el Architecture Handbook es lo que hace posible reconstruir el timeline completo de decisiones de un usuario sin recorrer toda la tabla.

Alertas y Health Checks

futuro — no existe ninguna ruta /api/health ni sistema de alertas activo (ni siquiera un webhook a Slack/email ante un console.error). Primer candidato de implementación cuando el volumen de usuarios lo justifique: alerta ante fallo repetido del proveedor de email (Brevo), porque hoy ese fallo solo es visible revisando logs manualmente.
