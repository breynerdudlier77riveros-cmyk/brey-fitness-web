ENG-ADR-04 — RLS es la barrera real AR-018 aplicado — Sprint 0

RLS como barrera real, no el código de aplicación

Sin ENABLE ROW LEVEL SECURITY, las políticas de una tabla nunca se evalúan y cualquier poseedor de la anon key puede leer/escribir todo — "el error más común y silencioso de Supabase" (Security Handbook, Engineering 08). Toda tabla de este documento asume RLS como la barrera de autorización de última instancia; una comprobación de ownership en una Server Action es una conveniencia de UX (mensaje de error temprano), nunca el único guardarraíl (ENG-ADR-04).

AR-018 — aplicado en Sprint 0

workouts / workout_logs ya no permiten DELETE

Las políticas originales de workouts/workout_logs eran "CRUD propio" (for all) — más permisivas de lo que la Inmutabilidad de historial (FT-09) exige. M1 (Implementation Handbook, 05; IMP-ADR-04) quedó aplicado: workout_logs → solo select+insert propios; workouts → select+insert+update propio (limitado en la práctica a la transición de estado, aunque RLS de Postgres no restringe por columna). El delete desapareció de ambas — ver supabase/schema.sql y supabase/migration_rls_endurecimiento.sql.

Brecha real y conocida — profiles sin distinción de columna

La política de UPDATE de profiles no distingue quién escribe qué columna

La política real permite editar cualquier columna propia — incluidas sistema_actual/nivel_actual, que deberían escribirse exclusivamente por el proceso de Diagnóstico/Motor BPS (03, 04). Postgres RLS no restringe por columna de forma nativa — cerrar esta brecha requiere un mecanismo adicional (trigger de validación, o un camino de escritura de servidor separado con su propia autorización) no especificado todavía por ningún handbook. Se documenta como riesgo heredado, no resuelto aquí (16).

El único acceso sin autenticación — resolución de token

La resolución token → Reporte de bcs_enlaces_publicos/bcs_mediciones es la única operación de todo el ecosistema ejecutable por un actor sin sesión (Security Handbook, Engineering 08; BCS Handbook, 10) — condicionada estrictamente a que el token exista y su estado sea activo. El dominio nunca ve el token en sí mismo dentro de la capa de negocio — su resolución vive en la capa de aplicación (BCS Handbook, IN-A2).
