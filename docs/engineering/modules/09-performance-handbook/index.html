Módulo 09 · Calidad y operación

Performance Handbook

BREY corre en el modelo por defecto de Next.js App Router — SSR con streaming automático. No hay ISR, no hay memoización manual, no hay code-splitting explícito: correcto para la escala actual, con el umbral exacto de cuándo dejaría de serlo.

SSR y Streaming

Todas las rutas de /app/* son Server-Side Rendered en cada request (dependen de cookies() para la sesión — incompatibles con generación estática). El streaming es automático vía la convención de archivo loading.tsx de Next.js, no vía <Suspense> manual: app/app/loading.tsx es un Skeleton (13) que reconstruye la silueta completa del shell (sidebar + header + contenido) mientras layout.tsx resuelve getUser() + el perfil — evita salto de layout (CLS) cuando el contenido real aparece.

Lazy Loading

futuro — ningún componente usa next/dynamic hoy; todo el árbol de componentes se envía en el bundle inicial de su ruta. Aceptable a la escala actual (bundles pequeños, sin componentes pesados tipo editor de texto rico o gráficos 3D). Umbral de creación: el primer componente que dependa de una librería >50kb gzipped usada en menos del 30% de las cargas de esa ruta — un candidato futuro real son los gráficos de tendencia del BCS Design System Handbook (11) si su librería de charting resulta pesada.

ISR y Cache

futuro — sin export const revalidate en ninguna ruta. Las páginas de marketing (/sistemas, /ejercicios) son candidatas naturales a ISR porque su contenido cambia con poca frecuencia y hoy se sirven completamente dinámicas sin necesidad real — se documenta como oportunidad de optimización, no como bug (15).

Optimistic UI

futuro — ninguna mutación hoy actualiza la UI antes de la confirmación del servidor; todo formulario espera la respuesta de la Server Action. Es la decisión correcta para datos de salud/entrenamiento (mostrar un peso "optimista" que luego resulta rechazado por un CHECK de rango físico sería confuso) — este handbook recomienda explícitamente NO adoptar Optimistic UI para ninguna mutación sobre datos de composición corporal o entrenamiento, y sí considerarlo en el futuro solo para interacciones puramente de UI (ej. colapsar un Accordion).

Memoización

futuro — cero usos de useMemo/useCallback/React.memo en todo el código hoy. Correcto: ningún componente actual tiene un cálculo costoso en render ni un problema de re-render medido. Regla de este handbook: la memoización se añade en respuesta a un problema de rendimiento observado (11), nunca preventivamente — memoizar sin medir es la forma más común de sobre-ingeniería en React y contradice FT-10/FT-11 aplicadas sin necesidad real.

Queries e Índices

Detalle completo de índices en 05 — la regla de performance aquí es: ningún repositorio hace una consulta dentro de un bucle (N+1). Los repositorios actuales (profile/, workouts/) son consultas únicas por invocación; cualquier caso de uso futuro que necesite datos de múltiples tablas relacionadas debe resolverse con una sola consulta con select anidado de PostgREST, no con N consultas secuenciales.

Paginación y Carga incremental

Ver 06 — no implementado hoy, especificado como paginación por rango de fechas (no OFFSET/LIMIT) para el primer caso de uso real (Histórico del BCS Handbook, 12).

Compresión

implementado (por la plataforma) — la compresión de assets y respuestas HTTP la gestiona automáticamente la plataforma de despliegue (12), sin configuración manual en el proyecto.
