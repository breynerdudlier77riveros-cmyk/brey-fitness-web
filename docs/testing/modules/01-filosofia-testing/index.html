Filosofía de Testing

El dominio de BREY se diseñó testeable antes de tener un test runner. Este módulo explica por qué eso es cierto, y por qué significa que el plan de pruebas de la mayoría del ecosistema ya está escrito — dentro de los propios handbooks de dominio, no en este documento.

FT-08 Testabilidad · FT-03 Determinismo (Engineering Handbook) Estado real: 0 dependencias de testing, 0 archivos de test

Por qué el dominio ya es testeable sin test runner

FT-08 (Testabilidad) y FT-03 (Determinismo) ya obligan a que los motores de dominio sean funciones puras — sin import de Supabase, sin Date.now() implícito (Engineering Handbook, 10). Motor BPS exige fecha del ciclo como parámetro explícito (BPS-022); Progression Engine nunca hace su propio I/O (IN-P1); Recovery Engine recibe su ventana ya leída. Esto significa que, el día que se instale un test runner, la lógica más crítica de BREY ya es testeable sin mocks de base de datos: entrada in, salida out, siempre la misma salida para la misma entrada.

El plan de pruebas ya está escrito

La fuente de cada caso de prueba no es este documento

Cada regla PE-XXX de Progression Engine Handbook (07) ya incluye "Ejemplo válido" y "Ejemplo inválido". Cada transición T1-T15 de Motor BPS Handbook (05) ya incluye guard y efecto. Cada caso límite de cada handbook de dominio ya es, en la práctica, una fila de una tabla de pruebas — este documento no redacta esos casos de cero: los organiza en matrices verificables, nivela cada uno (unit/integration/e2e) y señala los que dependen de una brecha todavía abierta (16).

Ningún nivel se introduce fuera de orden. Un E2E no compensa la ausencia de Unit en los motores — cubre una superficie distinta (flujo completo de usuario), no reemplaza la verificación de una regla PE-XXX aislada (02).

Determinismo como precondición de testing, no como consecuencia

Un motor no determinista no es "difícil de testear" — es imposible de testear con confianza: un test que a veces pasa y a veces falla con la misma entrada no prueba nada, solo genera ruido. Por eso Motor BPS Handbook exige fecha del ciclo y versión de catálogo como parámetros explícitos (BPS-022) antes de que exista un solo test — el determinismo no es una optimización para testing futuro, es la precondición sin la cual ningún test de este documento tiene sentido (03).

Replay como forma de prueba

La máquina de estados de Motor BPS es recomputable desde cero a partir de progression_events (Motor BPS Handbook, pseudocódigo recomputarEstado; Database Handbook, 08). Esto convierte el replay en una técnica de prueba de primera clase, no solo en un mecanismo de producción: un test puede construir una secuencia de eventos conocida y verificar que el estado recomputado coincide exactamente con el esperado — sin necesitar ejecutar la lógica de negocio que originalmente los produjo (08).

Fail Visible como requisito de prueba

FT-05 (Fail Visible) exige que un repositorio devuelva null/[] explícito, nunca una excepción no capturada (Architecture Handbook, 11). Todo test de este documento que ejercite un camino de "no encontrado" o "sin datos suficientes" verifica ese valor explícito — un test que solo cubre el camino feliz no cumple con la filosofía de este documento, sin importar cuánto "código" cubra numéricamente (13).
