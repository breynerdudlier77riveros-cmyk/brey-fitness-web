Módulo 11 · Calidad

Observabilidad

Orden de instrumentación: logs antes que eventos de dominio, eventos antes que métricas agregadas, métricas antes que alertas. Nunca al revés — una alerta sobre una métrica que no se está registrando todavía es ruido, no señal.

Orden exacto

  1. Logs — cada Route Handler y repositorio nuevo sigue la convención ya real (console.warn/console.error con prefijo [contexto], Engineering Handbook 11) desde su primera versión, no como mejora posterior.
  2. Eventos de dominio — cada Decisión de Motor BPS/Progression Engine se persiste en progression_events con contexto completo desde la primera implementación de cada regla (08) — no se difiere "para cuando haya tiempo de instrumentar".
  3. Resolución del esquema de contexto — antes de que la segunda regla de un mismo grupo (micro/macro/etc.) se implemente, el esquema de contexto para ese grupo debe estar fijado (Architecture Review, AR-013) — nunca cada regla inventando su propia forma de contexto sobre la marcha.
  4. Métricas — se derivan de progression_events ya poblada con datos reales (Engineering Handbook 11: tasa de avance/sostiene/retroceso, frecuencia de VENTANA_INSUFICIENTE) — no se construye un dashboard de métricas sobre una tabla vacía.
  5. Alertas — el último paso, y solo sobre condiciones ya observadas al menos una vez en logs/eventos reales (ej. fallo repetido de Brevo) — nunca una alerta especulativa sobre un caso que nunca ha ocurrido.

Checklist de instrumentación por pieza nueva

  • ¿Todo INSERT rechazado por un CHECK de base de datos queda registrado con console.error y prefijo de contexto? (Architecture Review, AR-027)
  • ¿El evento persistido incluye razones no vacío? (FT-06, IN-P5 del Progression Engine Handbook)
  • ¿El contexto sigue el esquema ya fijado para su grupo de reglas, no uno improvisado?
  • ¿Existe al menos un log de auditoría (quién, qué, cuándo) para cada escritura nueva, aunque sea en el formato mínimo ya real?
