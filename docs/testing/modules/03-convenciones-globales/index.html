Módulo 03 · Fundamentos

Convenciones Globales

Naming, organización, factories, fixtures, mocks y determinismo — las mismas reglas para cualquier suite futura, sin excepción por motor o superficie.

Naming

UnidadConvención
Archivo de testUno por unidad de dominio bajo prueba, nombrado igual que la unidad + sufijo de test — nunca un archivo de test que cubra dos motores distintos
Caso de testUn caso por fila de la tabla de casos límite del handbook de origen (ej. una fila de "Ejemplo inválido" de una regla PE-XXX = un caso) — el nombre del caso cita el ID de la regla/transición/constraint que verifica, nunca una descripción libre sin ese ID
FixtureNombrada por el escenario de dominio que representa (ej. "usuario en ventana insuficiente"), nunca por datos genéricos ("test1", "datosA")

Organización

La estructura de tests refleja la estructura de dominio, nunca la estructura técnica de carpetas de implementación — un test de Motor BPS vive junto al concepto "Motor BPS", no junto a "servicios" o "controladores" genéricos. Esto permite que cualquier regla nueva de un handbook de dominio tenga una ubicación de test obvia sin discusión de dónde colocarla.

Factories

Regla ya establecida — Engineering Handbook, 10

Una factory por DTO oficial (API Contract Handbook, 08) — nunca un objeto literal repetido en cada caso de test. Una factory produce un DTO válido por defecto, con la posibilidad de sobreescribir campos puntuales para el caso bajo prueba (ej. una factory de Prescripción que por defecto es válida, pero permite forzar un campo fuera de rango para probar el CHECK correspondiente).

Fixtures

Datos de referencia estables y versionados junto al test — nunca generados aleatoriamente en cada ejecución (Engineering Handbook, 10). Una fixture representa un escenario de dominio completo y conocido: por ejemplo, las respuestas completas de un Diagnóstico que produce un resultado ya documentado, o una ventana de historial de exactamente 4 apariciones (el mínimo de Progression Engine Handbook, IN-P3) para probar el límite exacto de VENTANA_INSUFICIENTE.

Mocks — qué se mockea y qué nunca

SituaciónRegla
Test unit de un motor puro (Progression Engine, Recovery Engine)Sin mocks — el motor recibe sus argumentos ya construidos por una factory, nunca necesita mockear nada porque no hace I/O (IN-P1)
Test unit de una Server Action aisladaSe mockea el SupabaseClient inyectado como parámetro — patrón ya permitido sin trabajo adicional porque el cliente ya viaja como argumento explícito (Architecture Handbook, 11)
Cualquier test integrationNunca se mockea Supabase completo — divergería de RLS real, exactamente el riesgo que este nivel existe para prevenir (02)
El Veredicto de Recovery como entrada de un test de Progression EngineSe construye con la factory del DTO canónico ({procede, subtipo?, razon}, API Contract Handbook 08) — nunca con una forma ad-hoc inventada por el test (06, TEST-ADR-02 en 14)

Determinismo — sin excepción de convención

ParámetroRegla en el test
Fecha del cicloSiempre un valor fijo explícito en la factory de entrada — nunca Date.now() ni una fecha relativa a "hoy" dentro de un test (Motor BPS Handbook, BPS-022)
Versión de catálogoSiempre fijada explícitamente — un test nunca depende de "la versión más reciente" del catálogo en código (Architecture Handbook, ADR-009)
Generación de IDsCuando el caso de prueba lo requiere (ej. verificar unicidad), el ID se fija explícitamente; cuando no importa, se acepta cualquier valor generado, pero nunca se asigna significado accidental a un ID aleatorio

Un test que no fija estos tres parámetros no es un test determinista — es una ejecución que casualmente pasó una vez. Ningún caso de las matrices de 04-12 se considera completo sin sus parámetros deterministas explícitos.
