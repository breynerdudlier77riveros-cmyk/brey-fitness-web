Módulo 10 · Estructura

Máquinas de Estado

Cinco entidades con estados reales — sus transiciones válidas, las que están explícitamente prohibidas, y cómo se recupera el sistema si aparece un estado corrupto.

Diagnóstico

stateDiagram-v2
  [*] --> en_curso
  en_curso --> completado
  completado --> [*]
Detalle
Transiciones válidasen_curso → completado, disparada al responder la última pregunta (DX-01)
Transiciones inválidascompletado → en_curso — un Diagnóstico terminado nunca se reabre; retomar significa crear un Diagnóstico nuevo (P3)
Recuperación ante estado corruptoUn Diagnóstico completado sin ResultadoDiagnóstico asociado es un estado corrupto (viola IN-12 en 12) — la recuperación correcta es tratarlo como si nunca hubiese llegado a completado, nunca inventar un ResultadoDiagnóstico a posteriori (rompería FT-03, determinismo)

Programa

stateDiagram-v2
  [*] --> sin_diagnostico
  sin_diagnostico --> pendiente_perfil : Diagnóstico completado
  pendiente_perfil --> activo : gate superado
  pendiente_perfil --> gate_fallado : campos de gate ausentes
  gate_fallado --> pendiente_perfil : perfil corregido
  activo --> sistema_completado
  sistema_completado --> [*]
Detalle
Transiciones válidasSecuencia completa según Motor BPS Handbook T3–T7, T14 — un Programa siempre nace de un Diagnóstico completado, nunca directamente activo
Transiciones inválidassin_diagnostico → activo (salto directo) — viola IN-05 en 12; sistema_completado → activo — un Sistema completado no se reactiva, un nuevo ciclo es un Programa conceptualmente distinto (nueva combinación Usuario+Sistema+fecha, CT-01)
Recuperación ante estado corruptoUn Programa "activo" cuyo Usuario no tiene sistema_actual apuntando a él es corrupto por definición — dado que Programa no tiene fila propia (13), su único estado real vive en profiles.sistema_actual/nivel_actual; la recuperación es siempre re-derivar desde esas columnas, nunca desde un caché o vista materializada

Workout

stateDiagram-v2
  [*] --> planificado
  planificado --> completado
  planificado --> perdido
  completado --> [*]
  perdido --> [*]
Detalle
Transiciones válidasplanificado → completado al registrarse un WorkoutLog vinculado; planificado → perdido al vencer su fecha planificada sin ejecución
Transiciones inválidascompletado → planificado y perdido → planificado — ambos son estados finales (CT-05); corregir una ejecución nunca reabre el Workout, crea un WorkoutLog nuevo (FT-09)
Recuperación ante estado corruptoUn Workout completado sin ningún WorkoutLog que lo referencie (workout_id) es corrupto — se trata como perdido para efectos de Progression Engine (nunca se asume cumplimiento sin evidencia, P8)

Medición

stateDiagram-v2
  [*] --> vigente
  vigente --> anulada
  anulada --> [*]
Detalle
Transiciones válidasvigente → anulada, disparada exclusivamente por una corrección (UC-06 del BCS Handbook) — la corrección crea una Medición vigente nueva en el mismo movimiento
Transiciones inválidasCualquier edición en sitio de una Medición vigente — prohibida sin excepción (FT-09); anulada → vigente — una Medición anulada nunca vuelve a estar vigente
Recuperación ante estado corruptoDos Mediciones vigente para el mismo Cliente en la misma fecha exacta violan IN-D del BCS Handbook — la recuperación es anular la más antigua de las dos, nunca ambas, y nunca elegir arbitrariamente sin dejar rastro de cuál se anuló y por qué

EnlacePúblico

stateDiagram-v2
  [*] --> activo
  activo --> revocado
  revocado --> [*]
Detalle
Transiciones válidasactivo → revocado, disparada por el Entrenador o por la creación de un nuevo enlace para el mismo Cliente (IN-D4 del BCS Handbook)
Transiciones inválidasrevocado → activo — un token revocado jamás se reactiva; compartir de nuevo siempre emite un token nuevo (BCS-ADR-02)
Recuperación ante estado corruptoDos EnlacesPúblicos activo simultáneos para el mismo Cliente violan 09-IN-1 del BCS Handbook — la recuperación es revocar todos menos el más reciente, nunca dejar la ambigüedad sin resolver
