Security Handbook

La regla que gobierna todo este módulo, ya real en el código: RLS es la barrera de seguridad verdadera; cualquier otra capa (proxy, chequeo en Server Action) es UX, nunca protección primaria.

Autenticación

Supabase Auth vía @supabase/ssr — sesión persistida en cookies httpOnly, refrescada automáticamente. Tres clientes distintos según el contexto de ejecución (04, BE-06): lib/supabase/server.ts (Server Components/Actions, usa cookies() de next/headers), lib/supabase/client.ts (Client Components), lib/supabase/proxy.ts (el proxy, opera sobre NextRequest/NextResponse directamente).

JWT — getUser() vs. getSession()

Regla ya documentada en el código real

getSession() solo lee la cookie — no garantiza que el JWT siga siendo válido. getUser() revalida contra el servidor de Auth. src/lib/supabase/proxy.ts usa getUser() explícitamente para la decisión de redirect, con el comentario en el propio código: "no basta con leer la cookie (getSession()) para una decisión de redirect". Cualquier código nuevo que necesite saber si el usuario está autenticado debe seguir el mismo criterio.

RLS — la barrera real

auth.uid() = user_id, en cada tabla de usuario
flowchart TD
  Q["Query a una tabla con RLS activo"] --> P{"¿Existe policy para esta operación?"}
  P -->|"No"| DENY["Denegado — comportamiento por defecto sin policy"]
  P -->|"Sí"| C{"¿auth.uid() = user_id de la fila?"}
  C -->|"No"| DENY2["Fila excluida del resultado"]
  C -->|"Sí"| ALLOW["Fila visible/editable"]

Advertencia ya presente en supabase/schema.sql: sin ENABLE ROW LEVEL SECURITY, las políticas de abajo nunca se evalúan y cualquiera con la anon key (pública, va en el JS del navegador) puede leer y escribir todo — "el error más común y silencioso de Supabase". Verificar RLS activo en cada tabla nueva no es opcional, es un paso obligatorio de cualquier migración (05). RLS como única barrera de seguridad real es decisión formal en ENG-ADR-04 (14).

Las políticas "CRUD propio" de workouts/workout_logs permiten DELETE al propio usuario — más permisivo de lo que el principio de inmutabilidad (FT-09) exige para datos de historial. Migración de endurecimiento ya especificada por el Architecture Handbook: workout_logs → solo select+insert propios; workouts → select+insert+update propio (limitado en la práctica a la transición de estado, aunque RLS de Postgres no restringe por columna — esa disciplina queda documentada, no forzada por Postgres). delete desaparece de ambas. Pendiente de aplicar — ver 15.

Storage y Buckets

futuro — Supabase Storage no está configurado (04, BE-07). Cuando se active para las fotografías del BCS Handbook (11), la regla ya especificada es: bucket separado, acceso solo vía referencia autenticada del entrenador o token de EnlacePúblico válido — nunca una URL de bucket pública y predecible.

Links Públicos y Tokens

especificado — el diseño completo del token de compartición vive en el BCS Handbook (10) y BCS-ADR-02: token alfanumérico aleatorio criptográficamente seguro, mínimo 21 caracteres, sin relación derivable con ningún dato del Cliente, ruta con noindex. Este handbook confirma que ese es el único patrón de "acceso sin autenticación" permitido en todo el ecosistema — ningún módulo futuro inventa su propio esquema de token sin pasar por esta misma especificación.

Rate Limiting

futuro — no implementado en ningún endpoint hoy, incluidos los 2 Route Handlers reales (/api/lead, /api/contacto). Riesgo real documentado en 07 del BCS Handbook (intentos de token inválido/revocado sin límite de tasa). Candidato técnico: Vercel Edge Config o un middleware de rate limiting a nivel de proxy.ts — decisión pendiente (15).

Convención de naming ya establecida

El prefijo NEXT_PUBLIC_ es la única señal de si una variable es segura para el navegador — cualquier variable nueva sin ese prefijo se trata como secreto de servidor por defecto, nunca al revés (un secreto no se marca "por ahora sin prefijo, ya lo cambio después").

Logs

Detalle de niveles y formato en 11 — a nivel de seguridad, la regla es que un log nunca incluye el valor de un secreto ni un token de EnlacePúblico en texto plano (BCS Handbook, 08: "nunca el token en texto plano en el log de auditoría — solo su identificador interno").

Auditoría

Detalle completo en 05/11. A nivel de seguridad: toda acción de escritura queda atribuible a un user_id real vía RLS + created_at — no existe hoy una tabla de auditoría formal separada de las tablas de negocio mismas.

Ataques comunes y mitigaciones

AtaqueMitigación real o especificada
RLS deshabilitado por accidente en una tabla nuevaAdvertencia explícita ya documentada en schema.sql; regla de este handbook: ninguna migración se considera completa sin verificar el indicador de RLS activo en el Dashboard
Enumeración de tokens de EnlacePúblicoLongitud mínima de 21 caracteres aleatorios (BCS-ADR-02) + rate limiting futuro pendiente
CSRF sobre Server ActionsMitigado por el propio modelo de Server Actions de Next.js (origen verificado por el framework) — no requiere token CSRF manual adicional
Open redirect en el proxyproxy.ts solo redirige a una ruta interna fija (/login), nunca a una URL tomada de un parámetro de la request
Fuga de SUPABASE_SERVICE_ROLE_KEYNo usada en ningún código hoy — el riesgo es cero mientras siga sin activarse; si se activa, regla de naming (arriba) la protege de exposición accidental al cliente
