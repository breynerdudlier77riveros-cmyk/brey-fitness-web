Módulo 00 · Empezar

Introducción

Cómo se verifica lo que los ocho handbooks existentes ya especifican — nunca qué construir, nunca una regla nueva. La especificación completa que cierra AR-024 (Architecture Review): cobertura de pruebas 0% no por falta de plan, sino por falta de ejecución.

Especificación de verificación, nunca implementación Sin Jest · sin Vitest · sin Playwright · sin SQL · sin TypeScript · sin pseudocódigo Cero reglas, algoritmos, APIs, tablas o DTOs nuevos

Propósito

Ocho handbooks ya especifican, con enorme detalle, qué debe pasar: 39 reglas de Progression Engine, 15 transiciones de Motor BPS, 45 endpoints, 42 constraints, 9 tablas con sus políticas de RLS. Ninguno responde, de forma unificada, la pregunta que precede a cualquier test real: ¿cómo se verifica que cada una de esas afirmaciones sigue siendo cierta, en qué nivel, con qué caso exacto, y contra qué matriz de cobertura? Este documento responde esa pregunta una sola vez, para todo el ecosistema — consolidando, nunca inventando, lo que esos ocho documentos ya implican como comportamiento correcto.

Alcance

  • La arquitectura de pruebas completa: niveles, convenciones, factories, fixtures, mocks, determinismo.
  • Una especificación de verificación por cada superficie del ecosistema: dominio, motores, máquinas de estado, eventos, base de datos, API, UI.
  • Las once matrices de trazabilidad exigidas: Regla→Test, Motor→Suite, Evento→Verificación, FSM→Casos, Endpoint→Integración, Tabla→Restricciones, RLS→Verificación, y los casos específicos de Recovery, Progression, Motor BPS y BCS.
  • El cierre documental de AR-024 (cobertura de pruebas 0%) y el tratamiento explícito, sin resolverlas, de AR-025, AR-026 y AR-013.
  • Una autoauditoría que además documenta — sin corregirlas — las contradicciones que esta construcción encontró en otros handbooks.

Jerarquía documental

Este documento se deriva únicamente de nueve fuentes: Architecture Handbook, Engineering Handbook, Database Handbook, API Contract Handbook, Motor BPS Handbook, Progression Engine Handbook, BCS Handbook, BCS Design System Handbook y Architecture Review v1.0. No inventa comportamiento que esas nueve fuentes no impliquen ya. Donde un hecho citado se originó en Domain Model Handbook o Implementation Handbook (ej. la forma canónica del Veredicto de Recovery, o el orden de migraciones), este documento lo cita a través de la fuente que ya lo consolidó dentro de las nueve permitidas — Database Handbook y API Contract Handbook — nunca lo redecide ni lo contradice, respetando la misma jerarquía que ya gobierna el resto del ecosistema:

Prioridad sobre la implementación

Regla de prioridad

Si una suite de pruebas futura contradice lo que este documento especifica — un caso omitido, un nivel de prueba equivocado para una regla — la suite está incompleta, no este documento. Frente a los ocho handbooks existentes, este documento no tiene autoridad para inventar un caso de prueba que ningún documento anterior ya implique — solo para nombrarlo, nivelarlo y hacerlo verificable.

Cómo leer este documento

Se reutiliza el sistema de etiquetas ya establecido en los handbooks anteriores para el estado de cada pieza:

implementado especificado futuro

Y se añade el vocabulario propio de este documento — el nivel de prueba que corresponde a cada caso (02):

unit integration e2e manual bloqueado

bloqueado marca un caso que no puede ejecutarse hoy porque depende de una brecha real todavía abierta en otro handbook (ej. el esquema de contexto) — se especifica igual, para que la implementación no lo descubra tarde.
