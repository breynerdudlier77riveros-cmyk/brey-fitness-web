Glosario

Todo el vocabulario técnico transversal, sinónimos aceptados, términos prohibidos y las confusiones más frecuentes entre este handbook y los de dominio.

Vocabulario técnico

TérminoDefinición
Application ServiceCapa que orquesta ≥2 repositorios/motores para un caso de uso (04) — futuro, no existe todavía
Bounded contextUn dominio de negocio con su propio vocabulario y modelo, sin compartir tipos con otro (02)
Domain ServiceMotor de dominio puro, sin I/O — lib/diagnostico/motor.ts es el único real hoy (04)
especificadoEtiqueta: contrato completo en un handbook de dominio, sin código que lo implemente (00)
futuroEtiqueta: ni siquiera especificado en detalle, candidato de roadmap (00, 15)
implementadoEtiqueta: existe en el código real, verificado contra el repositorio (00)
proxy.tsEl sucesor de middleware.ts en Next.js 16 — capa de UX, nunca la barrera de seguridad real (08)
progression_eventsLa única tabla de eventos de todo el ecosistema, especificada por el Architecture Handbook, aún no creada (05, 07)
RepositoryÚnico punto de acceso a una tabla/agregado, recibe el SupabaseClient como parámetro (04)
RLSRow Level Security de Postgres — la barrera de seguridad real de todo el sistema (08)
Server ActionFunción "use server", punto de entrada de una mutación desde el cliente (04)
SSoTSingle Source of Truth — FT-01, el principio de mayor precedencia junto a Fail Visible

Sinónimos aceptados

Términos equivalentesPreferido en este handbook
"Motor de dominio" / "Domain Service"Ambos válidos — "motor" cuando se habla en el contexto de un handbook de dominio (Motor BPS, Progression Engine), "Domain Service" cuando se habla de la capa arquitectónica (04)
"Función pura" / "sin efectos secundarios" / "determinista""Determinista" (FT-03) es el término formal; los otros dos son descripciones equivalentes aceptadas en prosa
"Endpoint" / "Route Handler""Route Handler" — es el término oficial de Next.js y evita ambigüedad con Server Actions, que no son endpoints HTTP tradicionales

Términos prohibidos

Término prohibidoPor quéUsar en su lugar
"Microservicio"BREY es un monolito Next.js desplegado como una sola unidad (02, 12) — el término sugiere una arquitectura que no existe"Módulo" o "bounded context"
"Base de datos" a secas cuando se habla de Postgres vs. SupabaseAmbigüedad real entre la base de datos (Postgres) y la plataforma que la aloja (Supabase, que también da Auth y Storage)"Postgres" para el motor de datos, "Supabase" para la plataforma completa
"API" sin calificar cuando se refiere a contratos internosBREY no tiene una API pública versionada (06) — decir "la API" sin contexto sugiere algo que no existe"Contrato interno", "Route Handler" o "Server Action" según corresponda

Confusiones frecuentes entre handbooks

ConfusiónAclaración
"BCS" puede referirse al handbook de dominio o al de diseño"BCS Handbook" = dominio (datos, reglas); "BCS Design System Handbook" = diseño visual — nunca "BCS" a secas en un contexto donde ambos podrían aplicar
nivel_actual vs. nivel_experienciaYa aclarado en el Architecture Handbook (ADR-003) y repetido aquí porque es el error más fácil de cometer: nivel_actual es asignado por el Diagnóstico/Motor BPS y acoplado a un Sistema; nivel_experiencia es autorreportado y sin uso algorítmico en ningún motor
"Evento" en este handbook vs. "evento" de analíticaUn evento de dominio (07) vive en progression_events con RLS por usuario; un evento de analítica (page view, clic) vive en Plausible — nunca se mezclan en la misma tabla ni en la misma conversación sin aclarar cuál
"Especificado" no significa "aprobado para implementar sin revisión"Un handbook de dominio especifica el contrato completo, pero la implementación real puede descubrir un caso no previsto — en ese caso, el handbook se actualiza primero (00), no se improvisa en el código y se deja el handbook desactualizado
