Módulo 04 · Entidades

Entidades de Diagnóstico

Cuatro entidades — el proceso de determinar el Nivel de entrada de un Usuario en un Sistema.

DX-01implementado

Diagnóstico

Descripción
El proceso completo de responder el cuestionario BPS — aggregate root de este contexto.
Identidad
Propia — id uuid, tabla real diagnoses
Estados
en curso (efímero, sin persistir hoy) → completado
Ownership
Un Usuario puede tener múltiples Diagnósticos a lo largo del tiempo (retomas) — todos se conservan, ninguno se sobrescribe (P3 del Architecture Handbook)
Reglas de vigencia
Un resultado expira a los 6 meses para efectos de activación de compra (Motor BPS Handbook, BPS-005 / MBPS-ADR-05) — el registro histórico nunca se borra, solo deja de ser "vigente" para ese propósito específico
Relación con Motor BPS
Motor BPS consume el nivelEntrada del Diagnóstico vigente en el momento de activación (T3/T4/T5) — nunca traduce niveles entre Sistemas distintos (MBPS-ADR-06)
DX-02implementado

Respuesta

Descripción
Una respuesta individual a una pregunta del cuestionario — parte del array respuestas (jsonb) de diagnoses.
Identidad
Posicional dentro del Diagnóstico — sin identidad propia fuera de él
Estados
Ninguno — inmutable desde su captura
Ownership
Pertenece exclusivamente a un Diagnóstico — nunca se comparte ni se referencia desde otro contexto
DX-03implementado

ResultadoDiagnóstico

Descripción
El resultado computado — Sistema recomendado, Nivel de entrada, razones — columnas razones/notas (jsonb) de diagnoses.
Identidad
1:1 con el Diagnóstico que lo produce, no una entidad separable
Estados
vigente → expirado (a los 6 meses, para efectos de activación únicamente — DX-01)
Ownership
Producido por el motor de Diagnóstico (función pura, FT-03) — nunca modificado después de su creación (FT-09, Inmutabilidad)
Reglas de vigencia
Ídem DX-01
Relación con Motor BPS
Es la única entrada que Motor BPS necesita del contexto Diagnostics para activar un Sistema
DX-04implementado

PerfilEntrenamiento

Descripción
El subconjunto de profiles relevante para entrenamiento (días por semana, lugar, lesiones, objetivo) — distinto del Perfil completo, que también incluye datos personales (nombre, email, avatar) sin relevancia algorítmica.
Identidad
1:1 con el Usuario — no es una tabla separada, es un subconjunto conceptual de columnas de profiles
Estados
Ninguno propio — cambia por edición directa del Usuario
Ownership
El Usuario es dueño y editor exclusivo — ningún motor lo escribe automáticamente
Reglas de vigencia
Sin expiración — a diferencia del ResultadoDiagnóstico, el PerfilEntrenamiento es siempre "el estado actual", no un snapshot histórico
Relación con Motor BPS
Los "campos de gate" (días/semana, lugar, ausencia de lesiones bloqueantes) condicionan la transición pendiente_perfil → activo (Motor BPS Handbook, T6) — su ausencia posterior dispara gate_fallado (T7)

La distinción que este módulo protege

nivel_actual vs. nivel_experiencia — el error de lenguaje más citado en todo el ecosistema

nivel_actual vive en el ResultadoDiagnóstico → aplicado por Motor BPS — acoplado a un Sistema específico, con uso algorítmico real. nivel_experiencia vive en el PerfilEntrenamiento — autorreportado, genérico, sin ningún uso algorítmico en ningún motor de BREY (ADR-003 del Architecture Handbook). Confundirlos produce recomendaciones incorrectas de contenido — es la razón por la que este módulo los separa en dos entidades distintas (DX-03 vs. DX-04) en vez de tratarlos como un solo "nivel" ambiguo.
