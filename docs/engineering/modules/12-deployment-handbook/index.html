Riesgo real: un solo proyecto de Supabase para todos los entornos

No hay evidencia en el repositorio de un proyecto Supabase separado para Preview/Local vs. Producción — .env.example no distingue entornos. Esto significa que probar en Preview probablemente escribe en la misma base de datos que ven los usuarios reales. Se documenta como riesgo operativo real, no como diseño intencional — candidato de resolución en 15.

Migraciones en el flujo de deploy

Las migraciones (05) no están automatizadas en el pipeline de deploy — un archivo migration_*.sql se pega manualmente en el SQL Editor de Supabase, en un paso separado y humano, no disparado por el git push. Esto implica que un deploy de código que asuma una columna nueva puede llegar a producción antes de que la migración correspondiente se haya aplicado — orden de operaciones que hoy depende de la disciplina del desarrollador, no de una garantía del sistema.

Feature Flags

futuro — ninguna librería de feature flags en package.json. Los cambios de features hoy se controlan enteramente por lo que está mergeado a main, sin capacidad de activar/desactivar en runtime. Los redirects de next.config.ts (ej. /programas → /sistemas) son el mecanismo real más cercano a un flag que existe hoy, y son permanentes, no conmutables.

Versionado

package.json declara "version": "0.1.0" — sin incrementarse automáticamente por release; no hay tags de git ni changelog formal encontrados en el repositorio. futuro: adoptar versionado semántico real solo se justifica el día que exista un consumidor externo de un contrato versionado (06) — hoy, con frontend y backend desplegados atómicamente juntos, no aporta valor operativo.

Variables de entorno por entorno

Detalle completo del catálogo de variables en 08. Regla de despliegue: toda variable nueva se añade primero a .env.example (documentada, sin valor real) antes de configurarse en el dashboard de Vercel — .env.example es la fuente de verdad de qué variables existen, nunca una lista mental o un README aparte.

Backups y Restore

futuro — ninguna política de backup documentada en el repositorio más allá de lo que Supabase ofrece por defecto en su plan. Se registra como pregunta abierta operativa (15): confirmar el plan de Supabase activo y su política de backups automáticos antes de tener datos de usuarios reales en volumen.

Monitoreo

Ver 11 para el detalle completo — a nivel de plataforma, Vercel expone métricas de build/runtime por defecto (tiempos de build, errores de función) sin configuración adicional; no hay una integración de monitoreo de aplicación (Sentry, Datadog) en package.json hoy.
