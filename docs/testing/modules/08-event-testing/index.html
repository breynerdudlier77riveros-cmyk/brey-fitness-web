El gap del CHECK — 14 reales, 25 consolidados

Prerrequisito de testing — no un caso de test en sí

El CHECK real de progression_events.tipo tiene 14 valores hoy; 11 de los 25 consolidados (Database Handbook, DB-ADR-03) dependen de la migración M2 todavía no aplicada. Ningún test de integration de un evento de esos 11 tipos puede ejecutarse hasta que M2 se aplique — se especifican aquí como bloqueado, no se omiten ni se simulan contra un CHECK que no es el real.

Idempotencia — gap real, no inventado (AR-027)

Sin clave de idempotencia especificada para el INSERT de un evento

Ningún handbook de origen define una clave de idempotencia para el INSERT de un EventoProgresión individual (Database Handbook, 10; AR-027). Este documento no inventa una — especifica que, hasta que exista, todo test de reintento de red sobre este INSERT debe documentarse como caso conocido sin cobertura posible, nunca como "ya probado" mediante una clave asumida.

El gap de contexto — AR-013 y AR-026, documentados sin resolver

Por qué esto bloquea una clase entera de test, no un caso aislado

contexto (jsonb) existe para habilitar el replay determinista, pero ningún handbook define su forma exacta por tipo de evento (AR-013). Sin ese esquema, no existe manera de escribir un test que verifique "este contexto es suficiente para reconstruir la decisión" — solo se puede verificar que el campo no está vacío, nunca que está completo (AR-026, ángulo de observabilidad). Este documento especifica exactamente qué se debe poder probar el día que el esquema exista (tabla abajo) — no lo inventa antes de tiempo.

Qué se podrá probar cuando el esquema de contexto existaNivelEstado hoy
Todo evento de un tipo dado tiene las mismas claves en contexto, nunca un subconjunto distinto entre dos instancias del mismo tipointegrationbloqueado

Los 10 eventos del BCS — verificación por efecto, no por fila propia

A diferencia de progression_events, los eventos del BCS (Database Handbook, 08) no tienen tabla de eventos propia — se verifican por su efecto persistido (ej. cliente_archivado se verifica comprobando que bcs_clientes.estado = 'archivado', no leyendo una fila de evento). Ver 06 (BCS → Casos) para el detalle por caso de uso.
