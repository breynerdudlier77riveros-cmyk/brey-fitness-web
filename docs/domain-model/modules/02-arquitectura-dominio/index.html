Arquitectura del Dominio

Siete bounded contexts. Cada uno con fronteras explícitas — qué puede importar de otro contexto, y qué le está prohibido.

Los siete bounded contexts

ContextoResponsabilidadEstado
IdentityUsuario, autenticación, perfil — la única fuente de identidad de todo el ecosistemaimplementado
DiagnosticsDiagnóstico, Respuesta, ResultadoDiagnóstico, PerfilEntrenamientoimplementado (motor), sin persistencia de resultado
Core TrainingPrograma, Bloque, Mesociclo, Microciclo, Workout, Slot, Ejercicio, Serieimplementado (Workout) / especificado (jerarquía superior)
ProgressionPrescripción, EvaluaciónProgresión, EventoProgresión — el dominio de Motor BPS + Progression Engineespecificado
RecoveryEstadoRecuperación, SeñalFatiga, Descargaespecificado (contrato mínimo únicamente)
Body CompositionCliente, Medición, HistorialMediciones, EnlacePúblicoespecificado
ReportingReporte — hoy completamente subsumido dentro de Body Composition; sin superficie propia fuera de ese contextoespecificado (dentro de Body Composition únicamente)
Reporting no es hoy un contexto independiente en la práctica

Se documenta como contexto propio porque conceptualmente es un eje distinto (presentar datos, no poseerlos) — pero su única instancia real hoy es el Reporte del BCS Handbook (04), que vive enteramente dentro de Body Composition. Si Motor BPS o Progression Engine desarrollan su propia superficie de reporte en el futuro (Engineering Handbook, 11 — métricas y KPIs), ese sería el segundo miembro real de este contexto — no se anticipa aquí.

Dependencias permitidas

ContextoPuede depender de
DiagnosticsIdentity (necesita saber de qué Usuario es el resultado)
Core TrainingIdentity, Diagnostics (el Nivel de entrada viene del Diagnóstico)
ProgressionRecovery (Veredicto) — nunca Core Training directamente como dependencia bloqueante, solo como invocador (Implementation Handbook, 02)
RecoveryNinguno — es una hoja del árbol de dependencias
Body CompositionIdentity (solo la identidad del Entrenador, nunca datos de Core Training)
ReportingBody Composition (su único miembro real hoy)

Dependencias prohibidas

  • Body Composition nunca depende de Core Training, Progression, Diagnostics o Recovery — el BCS Handbook (00, 01) ya lo declara explícitamente como standalone.
  • Recovery nunca depende de Progression ni de Core Training — invertiría la escalera de precedencia de seguridad (P8) que ambos handbooks de motor ya establecen.
  • Ningún contexto importa un tipo de dominio de otro directamente — solo consume su contrato de salida (DTO/evento), nunca su modelo interno (FT-13 del Engineering Handbook, aplicado al dominio).
  • Identity nunca depende de ningún otro contexto — es la raíz de todo el árbol.
