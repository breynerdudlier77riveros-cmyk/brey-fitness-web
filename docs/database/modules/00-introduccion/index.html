Introducción

La especificación oficial de persistencia de BREY — qué tabla existe, quién la posee, qué columna tiene, qué la restringe. La única fuente de verdad de persistencia para cualquier esquema físico futuro. No escribe SQL, no genera migraciones, no crea tablas.

Contrato de datos, nunca implementación Sin SQL · sin Prisma · sin Drizzle · sin migraciones Cero tablas/columnas/relaciones inventadas

Propósito

Ocho handbooks ya especifican, cada uno desde su propio ángulo, un dato que alguien tendrá que persistir: un Perfil, un Diagnóstico, un EventoProgresión, una Medición. Ninguno responde, de forma unificada, las preguntas que preceden a cualquier esquema físico: ¿qué tablas existen en total, quién es dueño de cada una, qué columna exacta tiene, qué la restringe, qué índice la sirve, y quién tiene prohibido tocarla? Este documento responde esas preguntas una sola vez, para todo el ecosistema, consolidando — nunca inventando — lo que los ocho documentos ya implican.

Alcance

  • El mapa completo de tablas ya implícitas en los handbooks de dominio, motor y BCS — con su bounded context dueño y su aggregate root.
  • Cada columna ya especificada de cada tabla — tipo lógico, nullable, unidad, default, origen y consumidores.
  • Las relaciones (FK lógicas), índices, constraints y políticas de RLS ya implícitos o ya reales.
  • Cómo se persisten los eventos de dominio (progression_events), y qué garantiza su replay.
  • Consistencia, evolución de esquema, performance y seguridad de datos — lo ya decidido y lo honestamente pendiente.
  • La documentación explícita de toda discrepancia entre handbooks que afecte al modelo persistente, vía DB-ADR (15) — sin resolverla inventando una forma nueva no autorizada por ningún documento superior.

Jerarquía documental

Este documento respeta, sin excepción, los ocho handbooks de BREY que sí tienen huella en el modelo persistente: Architecture Handbook, Domain Model Handbook, Engineering Handbook, API Contract Handbook, Motor BPS Handbook, Progression Engine Handbook, BCS Handbook y BCS Design System Handbook (sin huella de datos propia, ver 02). Recovery Engine Handbook no existe todavía (AR-006) — se cita como ausencia, no se completa por inferencia. Donde dos de ellos entran en conflicto sobre un mismo hecho de persistencia, la precedencia es:

Este handbook nunca contradice a ninguno de los tres niveles superiores. Donde el Architecture Handbook (10) y el Engineering Handbook (05) ya documentan el esquema real tal como existe, este documento los cita como evidencia de que una decisión ya se sostuvo en producción — nunca reescribe ese hecho, lo eleva a especificación formal con su razón explícita. Donde el Domain Model Handbook (13) clasifica una entidad como Persistente, Derivable o Efímera, este documento adopta esa clasificación sin re-decidirla (03). Donde una discrepancia real existe entre documentos (el gap del CHECK de progression_events.tipo, 14→25 valores; la ausencia de columnas ensambladas para las 25 variables del BCS, AR-017), este documento no la resuelve inventando — cita la resolución ya tomada por el nivel más alto que decidió algo al respecto (Implementation Handbook, IMP-ADR-06) o la declara abierta (16).

Prioridad sobre la implementación

Regla de prioridad

Si un esquema físico futuro contradice lo que este documento especifica, el esquema está equivocado, no este documento. Frente a los ocho handbooks existentes, este documento no tiene autoridad para inventar una tabla, una columna o una relación que ningún documento anterior ya implique — solo para nombrarla, tiparla y formalizarla como especificación única.

Toda ficha, columna, constraint e índice de este documento cita su origen exacto (handbook y módulo). Donde esa razón no existe todavía, la pieza no se documenta como decidida — se documenta como pregunta abierta (16).
