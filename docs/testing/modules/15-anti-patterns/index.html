Anti-patterns

17 formas reales de que un test mienta sobre lo que prueba — cada una ya evaluada y descartada por algún handbook, o directamente derivada de un caso real de este documento.

17 anti-patterns
#Anti-patternPor qué está prohibidoEvidencia
1Mockear Supabase completo en un test de integrationDiverge de RLS real — el nivel Integration existe exactamente para prevenir estoEngineering Handbook, 10; 02 de este documento
2Probar un motor sin fijar fecha_ciclo/versión de catálogoUn test que a veces pasa y a veces falla con la misma entrada no prueba nadaMotor BPS Handbook, BPS-022; 01, 03
3Saltarse la verificación de RLS "porque el test de unit ya pasó"Unit nunca toca RLS — son capas de riesgo completamente distintas (02)Engineering Handbook, 10 ("lista roja")
4Asertar sobre el texto en prosa de un mensaje de error en vez de su códigoEl texto puede cambiar por i18n/copy sin que el comportamiento cambie — el código es el contrato realAPI Contract Handbook, 09
5Snapshot-test de un jsonb sin considerar su discriminador de versiónUn snapshot que mezcla formas v1/v2 sin distinguirlas produce falsos positivos de regresiónDatabase Handbook, 11
6Un test que depende del orden de ejecución de otros testsRompe aislamiento — un test debe pasar o fallar igual sin importar qué corrió antes02 de este documento (ciclo de vida de datos)
7Reutilizar filas creadas por un test anterior sin limpieza deterministaContamina el estado conocido que el siguiente test asume — fuente clásica de fallos intermitentes02 de este documento
8Inventar un criterio de desempate para PE-012 "solo para poder escribir el test"Congela en el test una decisión de negocio que el propio Progression Engine Handbook no ha tomado (AR-008)TEST-ADR-09 (14)
9Escribir un test e2e para algo ya cubierto por unitRedundancia que no añade señal, solo costo de mantenimiento — viola la prioridad de introducción (01)Engineering Handbook, 10
10Confundir cobertura de código alta con cobertura de especificación completaUn 100% de líneas ejecutadas en lib/utils.ts no dice nada sobre si PE-012 está bien probado13
11Probar únicamente el camino feliz, omitiendo el camino de Fail VisibleFT-05 exige null/[] explícito — un test que no lo verifica no prueba la mitad del contrato01, FT-05 (Architecture Handbook)
12Escribir el test de DELETE de workouts/workout_logs contra el estado real permisivo, como si fuera el deseadoCongela una brecha de seguridad conocida (AR-018) como comportamiento aceptadoTEST-ADR-07 (14)
13Probar Recovery Engine como si su lógica de fatiga ya existieraDa falsa confianza sobre una decisión de negocio que no está especificada (AR-006)TEST-ADR-12 (14)
14Generar fixtures con valores aleatorios en cada corridaUn fallo intermitente sin fixture reproducible es casi imposible de depurarEngineering Handbook, 10; 03
15Tratar un test que cruza una frontera de bounded context prohibida como "caso feliz"La frontera existe para no cruzarse — el resultado esperado de intentarlo es siempre rechazo, nunca éxito05 (fronteras de contexto)
16Introducir un test runner antes del primer motor de dominio real implementadoDependencia sin valor inmediato — el runner se introduce junto con la primera implementación real, no antesENG-ADR-06 (Engineering Handbook)
17Escribir todo como e2e "para estar más seguros"Invierte la pirámide de prioridad — el nivel más costoso de mantener se vuelve el más usado, exactamente al revés de lo especificado01, 02
