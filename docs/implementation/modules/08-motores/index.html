Recovery Engine — contrato mínimo

No es el handbook completo — es lo mínimo para desbloquear a sus dos consumidores

Recovery Engine no tiene handbook de dominio propio (Architecture Review, AR-006). Escribirlo completo no es responsabilidad de este documento. Lo que sí resuelve este handbook, vía IMP-ADR-01 (14), es la forma exacta del veredicto que sus dos consumidores (Motor BPS, Progression Engine) necesitan para no bloquearse mutuamente por una ambigüedad de contrato (AR-001). La lógica interna de Recovery Engine (cómo decide) queda fuera de alcance hasta que exista su propio handbook — para la Fase 1 (03), su implementación puede ser deliberadamente simple (ej. siempre procede: true) sin romper el contrato que Motor BPS/Progression Engine consumen.

Orden interno de construcción: pipeline base (9 pasos) antes que las 39 reglas individuales — el pipeline sin reglas es testeable de inmediato (siempre "sostiene", sin lógica de negocio real), y cada regla se añade incrementalmente sin tocar el esqueleto. Dentro de las reglas, orden sugerido por el propio catálogo: microprogresión (PE-001–012) → macroprogresión (PE-013–018) → autorregulación (PE-019–026) → estancamiento (PE-027–032) → deload (PE-033–039), porque cada grupo posterior depende conceptualmente de que el anterior ya funcione (el deload, por ejemplo, presupone que el estancamiento ya se detecta correctamente).

Qué se paraleliza dentro de esta pista

Una vez el contrato de Recovery está fijo (IMP-ADR-01), Motor BPS (orquestador) y Progression Engine (lógica pura) pueden construirse por personas/equipos distintos en paralelo — se integran recién en el paso 14 de 04 (09, Integración). Esto es una consecuencia directa de la corrección de dependencia de 02: Progression Engine nunca depende de Motor BPS para existir, solo Motor BPS necesita que Progression Engine ya exista quien lo invoque en producción.
