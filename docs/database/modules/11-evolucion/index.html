Módulo 11 · Operación

Evolución

Cómo cambia el esquema sin romper lo que ya existe — el patrón real de migraciones, el orden ya secuenciado de las cuatro pendientes, y qué hace incompatible un cambio.

Patrón de migraciones — real, en uso

Archivos migration_*.sql planos e idempotentes: ADD COLUMN IF NOT EXISTS para columnas; para constraints (sin IF NOT EXISTS nativo en Postgres), un bloque DO $$ que verifica pg_constraint por conname + conrelid antes de crear. Cada archivo puede aplicarse N veces sin error — la idempotencia del propio archivo de migración, no solo de la operación de negocio que describe (Architecture Handbook, 10).

schema.sql paralelo mantiene el estado completo para instalación desde cero, actualizado en el mismo cambio que cada migración real — producción solo recibe migraciones, schema.sql nunca se re-aplica sobre datos existentes.

Backfill

Sin backfill especificado — las tablas están vacías hoy

Ningún handbook especifica una estrategia de backfill porque, a la fecha, las tablas de producción están vacías o casi vacías (Architecture Handbook, 10: "irrelevante con tablas vacías"). El caso donde sí importaría — la extensión pendiente profiles.zonas_riesgo (04) — no tiene todavía una estrategia de backfill definida para usuarios existentes; se registra como pregunta abierta (16).

La evolución de formas jsonb (workouts.ejercicios, workout_logs.ejercicios) es aditiva con un campo discriminador v cuando la forma cambia — los mappers de la capa de repositorio leen todas las versiones históricas, pero escriben solo la vigente (P3: lo ya escrito no se migra en masa). La forma actual de workouts.ejercicios descrita en 04 es la precursora (EjercicioPlan); la migración a la forma completa (v-Generator, con Patrón×Rol) es aditiva y solo afecta filas nuevas, porque la tabla real está vacía hoy.

Versionado del catálogo

El catálogo rico (Sistemas ricos, Ejercicios, plantillas) vive en código, versionado por git — nunca en la base transaccional (Architecture Handbook, ADR-009; Domain Model Handbook, 13). El evento semana_generada (08) registra qué versión de catálogo se usó para generar cada semana — es lo que hace una generación pasada reproducible (determinismo, P1) sin necesidad de un snapshot de base de datos.
