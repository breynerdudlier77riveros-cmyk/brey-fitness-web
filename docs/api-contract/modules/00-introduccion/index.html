Módulo 00 · Empezar

Introducción

El contrato oficial de todas las APIs del ecosistema BREY — qué endpoints existen, quién puede llamarlos, qué reciben, qué devuelven, qué eventos disparan. La única fuente de verdad para cualquier implementación futura de transporte (Server Action, Route Handler o API pública). No es un documento para programar.

Contrato, nunca implementación Sin código · sin SQL · sin TypeScript · sin Next.js Cero funcionalidad nueva

Propósito

Nueve documentos ya especifican, cada uno desde su propio ángulo, comportamientos que alguien tendrá que exponer como una operación invocable: crear un Cliente, registrar una Medición, evaluar una Progresión, cerrar una sesión de entrenamiento. Ninguno de los nueve responde, de forma unificada y transversal, la pregunta que cualquier implementador necesita antes de escribir la primera línea: ¿cómo se invoca esto, quién puede invocarlo, qué forma exacta tiene la entrada, qué forma exacta tiene la salida, y qué pasa si falla? Este documento responde esa pregunta una sola vez, para todo el ecosistema, consolidando — nunca inventando — lo que los nueve documentos ya implican.

Alcance

  • El catálogo completo de endpoints ya implícitos en los handbooks de dominio y motor — ruta, actor, entrada, salida, ownership, efectos secundarios y eventos.
  • Los DTO oficiales de entrada, salida, error, paginación y evento, en tablas — nunca en tipos de un lenguaje concreto.
  • Las convenciones globales de autenticación, autorización, HTTP, requests, responses, errores, versionado, idempotencia y rate limiting.
  • La documentación explícita de toda discrepancia entre handbooks que afecte a un contrato de API, vía API-ADR (15) — sin resolverla inventando una forma nueva no autorizada por ningún documento superior.
  • Las preguntas que este documento no puede cerrar porque dependen de un handbook que todavía no existe (Recovery Engine completo) o de una decisión de producto no tomada.

Jerarquía documental

Este documento respeta, sin excepción, los nueve handbooks ya existentes de BREY: Architecture Handbook, Motor BPS Handbook, Progression Engine Handbook, BCS Handbook, BCS Design System Handbook, Engineering Handbook, Architecture Review, Implementation Handbook y Domain Model Handbook. Donde dos de ellos entran en conflicto sobre un mismo contrato, la precedencia es:

Este handbook nunca contradice a ninguno de los cuatro niveles superiores. Donde el Engineering Handbook (resto) y este documento describen la misma pieza — por ejemplo, el catálogo de errores de app/api/lead, o la forma de progression_events — este documento la expande con el detalle que su propio encargo exige (más de un endpoint, más de un actor, más de una convención transversal), sin sustituir lo que el Engineering Handbook ya afirma. Donde una discrepancia real existe entre dos documentos de igual o distinto nivel (el caso más grave: la forma del Veredicto de Recovery, AR-001), este documento no la resuelve inventando una tercera forma — cita la resolución ya tomada por el nivel más alto que decidió algo al respecto (Implementation Handbook, IMP-ADR-01) y lo declara vía su propio API-ADR (15).

Prioridad sobre la implementación

Regla de prioridad

Si una implementación futura (Server Action, Route Handler, endpoint de una API pública) contradice lo que este documento especifica, la implementación está equivocada, no este documento. Frente a los nueve handbooks existentes, este documento no tiene autoridad para inventar un endpoint, un DTO o un evento que ningún documento anterior ya implique — solo para nombrar, tipar y hacer invocable lo que esos documentos ya establecieron como comportamiento necesario.

Toda tabla de este documento cita su origen exacto (handbook y módulo). Ningún endpoint, campo o error aparece sin una razón de negocio ya escrita en otro lugar. Donde esa razón no existe todavía, el endpoint no se documenta como contrato cerrado — se documenta como pregunta abierta (16).
