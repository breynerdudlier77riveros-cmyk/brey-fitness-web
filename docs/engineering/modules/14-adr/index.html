Módulo 14 · Estándares y gobernanza

Decisiones de Arquitectura (ADR)

Las decisiones técnicas transversales de este handbook. Las decisiones de dominio (MBPS-ADR-*, BCS-ADR-*, BCSD-ADR-*) viven en sus propios handbooks — aquí solo las que gobiernan el ecosistema completo.

Aceptada
ENG-ADR-01

Sin capa de Application Services hasta que se necesite

Contexto: el patrón "empresarial" clásico separa Server Actions/Controllers de una capa de Application Services que orquesta repositorios (04).

Problema: introducir esa capa hoy, cuando cada Server Action real invoca exactamente un repositorio, sería una abstracción sin caso de uso que la justifique.

Alternativas descartadas: crear la capa preventivamente "para cuando se necesite" — contradice FT-10/FT-11 aplicadas sin necesidad real y el patrón ya evidenciado en el propio código (Sprint 4.1 explícitamente no construyó getProfileOrThrow() ni funciones de coerción sin un call site real que las pidiera).

Decisión: las Server Actions invocan repositorios directamente hasta que un caso de uso real orqueste ≥2 repositorios con lógica de coordinación no trivial (04, BE-02).

Consecuencias: el primer Application Service real será, casi con certeza, GenerarReporte del BCS Handbook — se documenta como el trigger explícito a vigilar.

Aceptada
ENG-ADR-02

String-union sobre enum nativo, en TypeScript y en Postgres

Contexto: tanto TypeScript (enum) como Postgres (CREATE TYPE ... AS ENUM) ofrecen un tipo enumerado nativo.

Problema: ninguno de los dos se usa en el código real — se usa type X = 'a' | 'b' en TS y text + CHECK en Postgres consistentemente.

Alternativas descartadas: adoptar los tipos nativos por "corrección académica" — el enum de TS tiene comportamientos de comparación/serialización menos predecibles que una unión de literales; ALTER TYPE ... ADD VALUE de Postgres tiene restricciones históricas de transacción que CHECK no tiene.

Decisión: string-union/text+CHECK es el estándar en ambas capas — formalizado en 05 y 13.

Consecuencias: añadir un valor nuevo a cualquier enumerado del sistema es una migración simple y simétrica en ambas capas, sin casos especiales.

Aceptada
ENG-ADR-03

Una única tabla de eventos para todos los motores

Contexto: el Architecture Handbook ya especificó progression_events como tabla única antes de que existieran el Motor BPS Handbook y el Progression Engine Handbook (07).

Problema: cada handbook de motor nuevo podría, en teoría, pedir su propia tabla de eventos.

Alternativas descartadas: una tabla por motor (motor_bps_events, progression_engine_events) — fragmentaría el timeline cronológico de un usuario en múltiples tablas, forzando un UNION costoso para cualquier vista agregada.

Decisión: progression_events sigue siendo la única tabla de eventos de todo el ecosistema; cada motor nuevo declara su propio valor de origen y extiende el CHECK de tipo — nunca crea una tabla paralela.

Consecuencias: el CHECK de tipo crecerá con cada motor nuevo (ya son 25 valores consolidados, 07) — se acepta ese crecimiento a cambio de una única fuente de verdad de eventos.

Aceptada
ENG-ADR-04

RLS es la barrera real; el proxy es solo UX

Contexto: Next.js 16 renombró middleware.ts a proxy.ts y lo documenta explícitamente como no confiable como única barrera de seguridad.

Problema: es tentador tratar la redirección del proxy como si fuera suficiente protección de una ruta.

Alternativas descartadas: confiar solo en el proxy y omitir RLS en tablas "protegidas por la ruta" — un bug en el proxy, o un acceso directo a la API de Supabase sin pasar por Next.js, expondría los datos sin ninguna otra barrera.

Decisión: RLS (05, 08) es la única barrera de seguridad de la que este sistema depende formalmente; el proxy existe exclusivamente para una mejor experiencia de usuario (redirect limpio en vez de una página con datos vacíos).

Consecuencias: toda tabla nueva debe tener RLS verificado activo antes de considerarse en producción, independientemente de si sus rutas ya están "protegidas" por el proxy.

Aceptada
ENG-ADR-05

jsonb para datos de forma variable, nunca para lo que se filtra por campo interno

Contexto: workouts.ejercicios y workout_logs.ejercicios son jsonb, no tablas normalizadas — ya un trade-off explícito documentado en schema.sql.

Problema: jsonb es flexible pero pierde índices/FK a nivel de campo interno.

Alternativas descartadas: normalizar workout_log_exercises desde el inicio — alcance no solicitado en la iteración que creó estas tablas, y una migración de jsonb a relacional es una operación conocida y aislada si se necesita después.

Decisión: jsonb se usa mientras nada dentro del campo necesite su propio índice o FK; el momento en que eso ocurra es la señal de normalizar (05).

Consecuencias: ninguna consulta actual filtra por un campo dentro de ejercicios — el día que una lo necesite, es la migración pendiente ya anticipada, no una sorpresa.

Aceptada
ENG-ADR-06

Determinismo del dominio antes que tooling de testing

Contexto: BREY no tiene test runner instalado (10), pero sus motores ya son funciones puras.

Problema: instalar un test runner sin tests reales que escribir sería una dependencia sin valor inmediato.

Alternativas descartadas: añadir Jest/Vitest "porque todo proyecto serio lo tiene" antes de tener el primer motor implementado en código — invertiría el orden: primero el motor puro y testeable por diseño, después las pruebas concretas.

Decisión: el test runner se introduce junto con la primera implementación real de un motor de dominio (Motor BPS o Progression Engine), no antes — pero el diseño ya garantiza (FT-03/FT-08) que ese día no requerirá refactorizar nada para volverse testeable.

Consecuencias: hoy, cobertura de tests = 0%, documentado sin eufemismos (10) — la deuda es real, la mitigación de diseño también.
