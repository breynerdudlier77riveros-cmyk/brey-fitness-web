Arquitectura de Pruebas

Los tres niveles, qué cubre cada uno, y el entorno que cada uno necesita — formalizado a partir de lo ya especificado en el Engineering Handbook (10).

Los tres niveles

NivelQué cubreEntornoPrioridad
unitMotores de dominio puros (Motor BPS, Progression Engine, Recovery Engine, Workout Generator), validadores, mappersNinguno — entrada in, salida out, sin proceso externo1
integrationRepositorios, RLS, constraints, endpoints del catálogo (API Contract Handbook, 07)Base de datos Supabase de test real — nunca un mock de Supabase, porque divergería de RLS real (Engineering Handbook, 10)2
e2eFlujos completos de usuario (registro → perfil → primer entrenamiento; entrenador → cliente → medición → reporte público)Aplicación desplegada completa, contra la misma base de test3

Entorno de test — aislamiento real, no solo declarado

Riesgo heredado — AR-022 de la Architecture Review

Preview/Local probablemente comparten el mismo proyecto de Supabase que Producción (riesgo ya documentado, no resuelto por este handbook). Todo test de integration o e2e de este documento asume un proyecto de Supabase de test separado de producción — si esa separación no existe todavía, ningún test de este nivel debe ejecutarse contra el proyecto real, sin excepción. Este documento no resuelve AR-022; lo hereda como precondición de entorno.

Árbol de decisión — qué nivel corresponde a un caso nuevo

Se recorre una sola vez por caso — el primer "sí" fija el nivel

Ciclo de vida de los datos de prueba

MomentoRegla
Antes de cada test de integrationEstado conocido — vía fixtures versionadas (03), nunca datos residuales de un test anterior
DuranteEl test opera únicamente sobre filas que él mismo creó o sobre fixtures compartidas de solo lectura — nunca sobre una fila creada por otro test en ejecución paralela
DespuésLimpieza determinista de lo creado por el test — nunca TRUNCATE global entre tests que corren en paralelo

Qué nunca se mezcla entre niveles

  • Un test unit que necesita una fila real de bcs_mediciones para pasar está mal clasificado — es un test de integration (04).
  • Un test integration que ejercita más de un endpoint en cadena para verificar un flujo de usuario está mal clasificado — es un test de e2e (10).
  • Ningún test de ningún nivel corre contra el proyecto de Supabase de producción, ni siquiera en modo lectura (AR-022, arriba).
