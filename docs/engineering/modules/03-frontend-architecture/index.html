Módulo 03 · Capas

Frontend Architecture

La estructura de carpetas completa — las que ya existen en el código real, y las que este handbook especifica como convención para cuando el proyecto crezca más allá de su escala actual.

Honestidad de escala

No todas las 12 carpetas que un frontend "de nivel empresarial" suele tener existen hoy en BREY — y eso es correcto para su escala actual, no una omisión. hooks/, contexts/, providers/, features/, services/, types/, styles/, assets/ y utils/ como carpetas dedicadas no existen: hay exactamente 1 hook custom (inline en AppShell.tsx), 1 contexto (idem), types.ts y utils.ts son archivos únicos de 189 y ~30 líneas respectivamente. Este módulo documenta la convención real de hoy y el punto exacto en que cada carpeta debería materializarse.

Las 12 carpetas

FE-01implementado

app/

Responsabilidad
Rutas del App Router de Next.js — páginas, layouts, route handlers, Server Actions co-ubicadas con su ruta
Puede contener
page.tsx, layout.tsx, loading.tsx, componentes Client de una sola ruta (ej. PerfilForm.tsx dentro de app/app/perfil/)
Nunca contiene
Lógica de dominio reutilizable entre rutas — eso vive en lib/
Dependencias permitidas
components/, lib/, data/
Dependencias prohibidas
Ninguna ruta importa de otra ruta directamente — la reutilización pasa por components/ o lib/
FE-02implementado

components/

Responsabilidad
Tres subcarpetas con jerarquía estricta: ui/ (primitivas shadcn generadas, nunca editadas a mano salvo vía CLI), brand/ (wrappers con la identidad de BREY — única vía de import para código de features), app/ y layout/ (composición específica de superficie)
Puede contener
Componentes de presentación puros — reciben props, no hacen fetch propio salvo excepción documentada (04)
Nunca contiene
Reglas de negocio, acceso directo a Supabase (salvo la excepción de Navbar.tsx, documentada en 04)
Dependencias permitidas
ui/ solo importable desde brand/; brand/ importable desde cualquier app/, layout/ o ruta
Dependencias prohibidas
Ningún componente de app/ (ruta) importa ui/ directamente, saltándose brand/
FE-03futuro

features/

Responsabilidad especificada
Agrupar por feature de negocio (ej. features/composicion-corporal/) cuando un bounded context (02) tenga suficientes componentes, hooks y lógica propia para justificar su propia carpeta en vez de dispersarse entre app/, components/ y lib/
Estado actual
No existe — cada bounded context de hoy (perfil, workouts, diagnóstico) es pequeño y vive distribuido en lib/<dominio>/ + su ruta en app/
Umbral de creación
Cuando un bounded context tenga ≥3 componentes propios + ≥1 hook propio + lógica de dominio no trivial — el Body Composition System (BCS Handbook) es el primer candidato real
Dependencias (cuando exista)
lib/<dominio>/, components/brand/ — nunca otra features/<otro-dominio>/ directamente
FE-04implementado

hooks/

Estado actual
No existe como carpeta dedicada — 1 hook custom (useSidebarCollapse) vive inline en components/app/AppShell.tsx, junto al contexto que expone, porque son indivisibles (FT-11, Alta cohesión)
Umbral de creación
Al segundo hook custom que no esté acoplado 1:1 a un solo componente
Responsabilidad especificada
Lógica de estado reutilizable entre componentes — nunca fetch de datos de servidor (eso es responsabilidad de Server Components/Actions, 04)
Dependencias prohibidas
Un hook nunca importa un componente — la dirección es siempre componente → hook
FE-05implementado

contexts/ y providers/

Estado actual
No existen como carpetas — SidebarCollapseContext es el único contexto de la app, definido junto a AppShell.tsx; MotionConfig/TooltipProvider/Toaster se montan directamente en app/layout.tsx sin una capa providers/ intermedia
Umbral de creación
Al tercer contexto propio de la aplicación (no de una librería de terceros)
Responsabilidad especificada
Estado verdaderamente global (tema, sesión de cliente) — nunca estado que un solo árbol de componentes necesita
FE-06implementado

lib/

Responsabilidad
Una subcarpeta por dominio (profile/, workouts/, diagnostico/, perfil/, supabase/, database/) — repositorios, validación, mappers, motores puros (FT-02)
Puede contener
Repositorios (04), funciones de validación, motores de dominio, clientes de infraestructura (supabase/server.ts, supabase/client.ts)
Nunca contiene
Componentes React, JSX de cualquier tipo
Dependencias permitidas
Otra carpeta de lib/ (ej. profile/repository.ts importa database/mappers.ts), @supabase/*
Dependencias prohibidas
lib/ nunca importa de components/ ni de app/ — la dependencia siempre va en un solo sentido (02, IN-E1 aplicado al frontend)
FE-07implementado

types/

Estado actual
src/lib/types.ts — un único archivo de 189 líneas con todos los tipos de dominio compartidos (Profile, Workout, WorkoutLog, enums)
Umbral de creación de carpeta
Cuando ese archivo supere ~400 líneas o mezcle tipos de dominios claramente no relacionados — entonces se divide por dominio (types/profile.ts, types/workout.ts), nunca antes
Regla mientras sea un archivo único
Un tipo usado por un solo módulo vive junto a ese módulo, no en types.ts — solo los tipos genuinamente compartidos entran ahí (FT-01, SSoT sin sobre-centralizar)
FE-08futuro

services/

Estado actual
No existe — no hay hoy ninguna integración con un servicio HTTP externo que justifique una capa de cliente propia (Plausible Analytics se integra vía <script> estático, no vía SDK)
Umbral de creación
Al primer servicio externo real que requiera autenticación, retry o manejo de errores propio — un futuro Coach IA consumiendo un LLM externo es el candidato más probable
Responsabilidad especificada
Adaptador de un servicio HTTP externo — nunca lógica de negocio, solo el contrato de comunicación
FE-09implementado

styles/

Estado actual
No existe como carpeta — un único src/app/globals.css con los design tokens (@theme inline, variables de shadcn) y las pocas animaciones custom del sitio
Por qué no se divide hoy
Tailwind v4 concentra la mayoría del styling como utilidades inline en JSX — un archivo CSS separado por sección duplicaría esa fuente de verdad sin necesidad real
Umbral de creación de carpeta
Si globals.css creciera con múltiples archivos de animaciones/temas — no anticipado en el roadmap actual (15)
FE-10implementado

assets/

Estado actual
public/ a nivel de raíz del proyecto (convención estándar de Next.js), no src/assets/ — imágenes estáticas servidas directamente por el App Router
Regla
Ningún asset se importa mediante un bundler de imágenes propio — public/ más el componente next/image es la única vía
FE-11implementado

utils/

Estado actual
src/lib/utils.ts — un único archivo con cn() (merge de clases Tailwind), iniciales(), fechaISOLocal()
Regla
Solo funciones puras, sin estado, sin dependencia de React ni de Supabase — cualquier función que necesite el cliente de Supabase pertenece a lib/<dominio>/, no aquí
Umbral de división
Mismo criterio que types.ts (FE-07) — por ahora un solo archivo es suficiente y dividirlo sería FT-10 (bajo acoplamiento) mal aplicado a algo trivial
FE-12implementado

data/

Responsabilidad
Catálogos estáticos que no ameritan una tabla de base de datos completa — data/sistemas.ts es el ejemplo real (los 5 Sistemas del BPS con su copy largo, iconos y colores; la tabla systems de Supabase, 05, es deliberadamente un catálogo liviano que referencia estos datos, no los reemplaza)
Regla
Un dato entra en data/ cuando cambiarlo no requiere una migración ni un usuario final — es contenido editorial versionado junto al código
