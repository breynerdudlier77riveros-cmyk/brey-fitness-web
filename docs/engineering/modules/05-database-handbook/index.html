Enums

Convención real: text + CHECK, nunca CREATE TYPE ... AS ENUM

Ninguna tabla de BREY usa un enum nativo de Postgres — todas usan text con una restricción CHECK (columna IN (...)). Ejemplo real: workouts.estado text not null default 'planificado' check (estado in ('planificado', 'completado', 'perdido')). Se elige así porque añadir un valor nuevo a un CHECK es una migración simple (ALTER TABLE ... DROP CONSTRAINT + ADD CONSTRAINT), mientras que ALTER TYPE ... ADD VALUE tiene restricciones históricas de Postgres (no se puede ejecutar dentro de una transacción en versiones antiguas) — la simplicidad de migración gana sobre la validación nativa del tipo. Decisión formal en ENG-ADR-02 (14).

JSONB

ColumnaContenidoTrade-off documentado
workouts.ejercicios, workout_logs.ejerciciosLista de ejercicios de la sesiónSe eligió jsonb en vez de una tabla normalizada workout_log_exercises deliberadamente para esta iteración — evita el alcance no solicitado de una tabla relacional adicional; migrar de jsonb a relacional es una operación conocida y aislada si el volumen de consultas lo exige más adelante
diagnoses.razones, .notas, .respuestasTrazabilidad del resultado del Diagnóstico (FT-06, Explicabilidad)default '[]'::jsonb — nunca nulo, siempre al menos un array vacío

Regla: jsonb se reserva para datos de forma variable o anidada que no se consultan individualmente por campo interno con frecuencia — en el momento en que un campo dentro de un jsonb necesita su propio índice o FK, es la señal de que debe normalizarse a columnas/tabla real.

Índices

Gap real, no ejemplo inventado

Hoy no existe ningún CREATE INDEX explícito más allá de las claves primarias (que Postgres indexa automáticamente). Con el volumen actual de datos esto es aceptable — se documenta como deuda técnica a vigilar (15), con la regla ya especificada para cuando se necesite: todo índice nuevo se crea con CONCURRENTLY en producción para no bloquear escrituras, y todo FK usado en un filtro de RLS (user_id en las 4 tablas con "CRUD propio") es el primer candidato cuando el volumen lo justifique.

Policies (RLS)

Detalle completo en 08 — la convención de nombres y el patrón "CRUD propio" (using (auth.uid() = user_id) with check (auth.uid() = user_id)) se define aquí porque es, ante todo, una decisión de modelado de datos: toda tabla de usuario tiene una columna user_id (o id en profiles) que la política referencia directamente, sin JOIN.

Soft Delete vs. Hard Delete

PatrónEstadoDónde
Hard deleteimplementadoon delete cascade desde auth.users — eliminar la cuenta de un usuario borra físicamente todos sus datos, sin período de gracia
Soft deleteespecificadoNinguna tabla actual lo usa — el BCS Handbook ya especifica el patrón Archivado (reversible) vs. Eliminado (irreversible, UC-04) como convención a seguir cuando un dominio lo necesite; se implementa con una columna estado text check (...), el mismo patrón ya usado en workouts.estado, nunca con una columna deleted_at nullable como único mecanismo (menos explícito para RLS)

Sin herramienta formal de migraciones

No hay Supabase CLI con migraciones versionadas automáticamente ni ninguna herramienta tipo Prisma Migrate/Drizzle Kit en package.json — las migraciones son archivos .sql pegados manualmente en el SQL Editor del Dashboard de Supabase. Es una limitación real, documentada como deuda técnica (15), no un patrón recomendado para escalar el equipo.

Idempotencia y Rollback

Idempotencia: todo trigger de creación usa ON CONFLICT ... DO NOTHING (FT-04). Rollback: futuro — no existe hoy un mecanismo formal de rollback de migración; revertir un cambio de esquema hoy requiere escribir un nuevo script .sql manualmente, sin automatización ni testing previo (10).

Auditoría e Historial

futuro — hoy solo existen created_at/updated_at, sin tabla de auditoría genérica que registre quién cambió qué. El patrón de auditoría completo (quién, qué, cuándo, valor anterior) ya está especificado en el BCS Handbook (08) y en el Motor BPS Handbook (13) para sus dominios respectivos — este handbook establece que cualquier tabla de auditoría futura vive en su propio dominio (bcs_audit_log, no una tabla audit_log compartida entre todos los dominios, consistente con FT-02).
