Autenticación

Quién es quién frente a este catálogo — JWT, cookies, los cuatro actores reales, y por qué "Admin" no es uno de ellos todavía. Consolidado del Security Handbook (Engineering, 08) y el Lenguaje Ubicuo (Domain Model Handbook, 01).

Supabase Auth vía @supabase/ssr getUser() ≠ getSession() ENG-ADR-04 — RLS es la barrera real

Mecanismo — JWT y cookies

Toda autenticación del ecosistema pasa por Supabase Auth, sesión en cookies httpOnly con auto-refresh. Tres clientes distintos, cada uno con su propio contexto de ejecución:

ClienteContextoUso en este catálogo
lib/supabase/server.tsServer Components / Server ActionsEjecuta la inmensa mayoría de los endpoints de este catálogo (07)
lib/supabase/client.tsClient ComponentsSolo para lectura reactiva ya autorizada por RLS — nunca para lógica de dominio
lib/supabase/proxy.tsProxy — opera sobre NextRequest/NextResponseDecide redirecciones de ruta según sesión — no participa en el contrato de datos de este catálogo
Regla — getUser(), nunca getSession(), para decidir identidad

getSession() solo lee la cookie — no garantiza que el JWT siga siendo válido. getUser() revalida contra el servidor de Auth. Todo endpoint de este catálogo que necesite saber "¿quién es el actor de esta request?" para efectos de ownership o autorización usa el criterio de getUser() (Security Handbook, Engineering, 08) — nunca el de getSession() a solas.

RLS — la barrera real, no la autenticación

La autenticación identifica al actor; quien decide qué fila ve o edita es Row Level Security en Postgres. Sin ENABLE ROW LEVEL SECURITY en una tabla, sus políticas nunca se evalúan y cualquier poseedor de la anon key puede leer/escribir todo — "el error más común y silencioso de Supabase" (Security Handbook, Engineering, 08; ENG-ADR-04). Todo endpoint de este catálogo asume RLS como la barrera de autorización de última instancia — la comprobación de ownership en la Server Action es una conveniencia de UX (mensaje de error temprano), nunca el único guardarraíl.

"Admin" no es un actor especificado — ver API-ADR-05

Ningún handbook existente define un rol de administrador transversal (superusuario sobre todos los Entrenadores, o sobre todo el ecosistema). El Security Handbook (Engineering, 08) es explícito: no existe una tabla de roles, y "no hay ningún rol 'admin' documentado en este handbook". Este documento no lo inventa — lo registra como pregunta abierta (AP-01, 16).

Ownership — la regla de acceso por recurso

RecursoRegla de ownership
profiles, diagnoses, workouts, workout_logs, progression_eventsauth.uid() = user_id — el Usuario ve y edita únicamente sus propias filas
systemsLectura pública, incluso para Anonymous — es catálogo, no dato personal
bcs_clientes, bcs_medicionesVisibles/editables únicamente por el Entrenador dueño — nunca por otro Entrenador, nunca directamente por el Cliente (BCS Handbook, 08)
bcs_enlaces_publicosCreación/revocación solo por el Entrenador dueño del Cliente referenciado; resolución token→Reporte es la única operación que un actor Anonymous puede ejecutar, y solo si el token existe y está activo (BCS Handbook, 08, 10)

Autorización — fronteras de contexto

Ningún token de sesión de Usuario autoriza acceso a datos de BCS de otro Entrenador, y ningún token de EnlacePúblico autoriza nada distinto de la lectura del Reporte de ese Cliente específico (BCS Handbook, 10). Cruzar estas fronteras no es un caso de negocio — es un error de autorización, catalogado en 09 y 13.
