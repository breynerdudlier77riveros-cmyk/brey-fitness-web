Módulo 12 · Operación

Rate Limiting

Ningún handbook existente define un límite numérico — ni el Security Handbook ni el Performance Handbook (Engineering, 08/09). Este documento no inventa cifras para completar la sección: documenta dónde importaría más, con qué mitigación real ya existe, y deja el resto como pregunta abierta (16, API-ADR-06).

Estado real — sin implementación en ningún endpoint

Ni los dos Route Handlers reales (/api/lead, /api/contacto) ni ningún repositorio o Server Action tienen rate limiting hoy. El Security Handbook (08) lo confirma explícitamente como "futuro". Cualquier valor concreto (peticiones por minuto, ventana de bloqueo) que este documento pudiera dar sería inventado — y el encargo que gobierna este handbook lo prohíbe expresamente.

429 — cuando exista

Si en el futuro se introduce rate limiting, la respuesta sigue el mismo envelope de error de 06: { ok: false, error: "rate_limited" } con status 429. Este documento fija la forma de la respuesta por consistencia con el resto del contrato — no fija el umbral que la dispara, porque ningún handbook lo ha decidido todavía.

Reintentos

Ningún handbook especifica una política de Retry-After ni de backoff exponencial. El único precedente real de reintento en todo el ecosistema es el de app/api/lead frente a Brevo — y ese fetch no tiene timeout ni retry explícitos tampoco (Engineering Handbook, 09, deuda técnica ya documentada). Este documento no inventa una política de reintento donde ninguna existe.

Candidatos de implementación (sin decidir)

El Security Handbook (Engineering, 08) menciona Vercel Edge Config o middleware en proxy.ts como posibles mecanismos, sin decidir cuál. Este documento no elige entre ellos — esa decisión pertenece a un ADR futuro del Engineering Handbook o del Implementation Handbook, no a este contrato.
