Módulo 02 · Dominio y datos

Modelo del Dominio

Entidades, agregados, value objects, casos de uso y las tres máquinas de estado del sistema. El vocabulario exacto que todo módulo posterior usa sin redefinir.

Entidades y agregados

EntidadTipoDescripción
ClienteAggregate rootPersona presencial del entrenador. Contiene datos identificativos (nombre, contacto opcional) y su ciclo de vida propio (activo/archivado).
MediciónAggregate root (referencia clienteId)Una captura puntual de composición corporal, con fecha y el catálogo completo de variables (03).
EnlacePúblicoAggregate root (referencia clienteId)Token de acceso de solo lectura al reporte de un Cliente (09, 10).
ReporteValue object generado, no persistidoVista computada a partir del Cliente y sus Mediciones vigentes — nunca se almacena como snapshot independiente, siempre refleja el historial actual (04).
Por qué tres agregados y no uno

Un único agregado "Cliente" que contuviera todas sus Mediciones dentro obligaría a cargar el historial completo cada vez que se toca cualquier dato del cliente, y crecería sin límite con el tiempo (12). Medición y EnlacePúblico son agregados propios, cada uno referenciando clienteId — más alineado con un historial ilimitado. Se documenta como BCS-ADR-01 en 16.

Casos de uso

UC-01

CrearCliente

Registra un nuevo Cliente en estado activo. Precondición: nombre no vacío. Postcondición: Cliente persistido con fechaAlta = ahora.

UC-02

EditarCliente

Actualiza datos identificativos de un Cliente existente. No afecta el historial de Mediciones ni los EnlacesPúblicos ya emitidos.

UC-03

ArchivarCliente

Transición reversible activo → archivado (05). Es la acción por defecto detrás de "Eliminar cliente" en el panel — preserva el historial íntegro.

UC-04

EliminarClientePermanentemente

Acción distinta e irreversible, reservada para solicitudes de derecho al olvido (11) — nunca el resultado de un clic accidental de "eliminar" en el flujo normal.

UC-05

RegistrarMedición

Crea una Medición nueva en estado vigente, asociada a un Cliente, con fecha y los valores del catálogo (03) que el entrenador haya capturado.

UC-06

CorregirMedición

Nunca edita en sitio: crea una nueva Medición vigente y marca la anterior como anulada, preservando ambas en el historial (05). Misma filosofía de inmutabilidad que el resto de los sistemas de BREY — decisión formal en BCS-ADR-03 (16).

UC-07

CrearEnlacePúblico

Genera un TokenPublico nuevo y un EnlacePúblico en estado activo para un Cliente (10).

UC-08

RevocarEnlacePúblico

Transición activo → revocado, irreversible para ese token específico — revocar y volver a compartir siempre implica UC-07 con un token nuevo (10).

UC-09

VisualizarReportePúblico

Resuelve un TokenPublico a su Cliente y devuelve el Reporte computado (04) — el único caso de uso invocable sin autenticación.

Invariantes de dominio

  • IN-D1: una Medición nunca se edita en sitio — toda corrección es una Medición nueva + anulación de la anterior (UC-06).
  • IN-D2: un Cliente Eliminado es terminal — no existe transición de vuelta, a diferencia de Archivado.
  • IN-D3: un Reporte nunca se persiste independientemente de sus Mediciones fuente — siempre se computa on-demand, por lo que jamás puede quedar desactualizado (04).
  • IN-D4: un EnlacePúblico revocado nunca se reactiva — compartir de nuevo siempre crea un token distinto (10, IN-L en el módulo 10).
  • IN-D5: ninguna Medición existe sin un Cliente válido — el clienteId es obligatorio y no nulable en todo el ciclo de vida de la Medición.

Contraejemplos

  • El sistema NO permite editar el peso de una Medición pasada directamente — solo mediante UC-06, que preserva la Medición original anulada.
  • El sistema NO borra físicamente una Medición al "eliminar cliente" (UC-03) — el historial se conserva mientras el Cliente esté archivado, no eliminado.
  • El Reporte NO tiene un botón de "guardar snapshot" en v1 — siempre es la vista más actual (04, 17 pregunta abierta sobre snapshots para casos de export).
