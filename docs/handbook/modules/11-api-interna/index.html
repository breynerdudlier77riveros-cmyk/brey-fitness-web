API Interna

Los contratos entre subsistemas: repositorios (la capa que ya existe), servicios (los motores como funciones tipadas), DTOs, eventos de dominio, catálogo de errores y política de versionado. Contratos antes que implementaciones (P13): todo lo especificado aquí es implementable en cualquier orden sin renegociar fronteras.

Contrato > implementación (P13) Errores tipados (P6) Evolución aditiva

Convenciones globales

  • Cliente como parámetro: toda función de repositorio/servicio recibe el cliente de datos como primer argumento — es lo que permite servir a contexto servidor y navegador sin duplicar lógica (patrón ya implementado y probado).
  • Resultado tipado: los servicios devuelven Resultado<T> = { ok: true, data: T } | { ok: false, error: ErrorDominio }. Los repositorios (capa de datos, sin decisiones) devuelven T | null / T[] — la semántica de error de dominio es de los servicios, no del acceso a datos.
  • Pureza de motores: Progression/Recovery son funciones puras (historial entra como argumento, ya leído) — no hacen I/O. El Motor BPS y el Generator orquestan el I/O a través de repositorios.
  • Coerción única: todo lo que sale de un repositorio ya pasó por su mapper (10) — ningún consumidor coerciona tipos jamás.

Eventos de dominio

En v1 los "eventos" son dos cosas concretas — y ninguna es un bus de mensajes (ADR-013): (1) filas de progression_events como registro auditable (P2/P3); (2) la cola local del Player (09) como mecanismo de captura/sync. Un pub/sub asíncrono solo entrará cuando exista un consumidor que lo necesite de verdad (notificaciones, analytics) — y se especificará entonces por ADR.

Regla — el error nombra qué falta

Todo error de dominio lleva payload estructurado con el detalle exacto (P6). "Algo salió mal" no existe en este catálogo.

Versionado de contratos

  • Aditivo dentro de v1: agregar campos opcionales a DTOs y errores nuevos al catálogo no versiona. Cambiar semántica o eliminar campos, sí.
  • Cambio breaking = contrato nuevo junto al viejo (ej. evaluarProgresionV2) + ADR + migración de consumidores + deprecación del viejo. Nunca mutación in-place de un contrato publicado.
  • Las formas jsonb versionan con discriminador v (10) — los mappers absorben la compatibilidad, los consumidores ven siempre el DTO vigente.
