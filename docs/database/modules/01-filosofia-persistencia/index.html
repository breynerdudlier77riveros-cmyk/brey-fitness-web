Filosofía de Persistencia

Los principios que gobiernan cada ficha de este documento. Ninguno es nuevo: cada uno ya se sostuvo en producción o en un handbook anterior — este módulo los hace explícitos para que la próxima decisión de datos no tenga que redescubrirlos.

FT-01 SSoT · FT-09 Inmutabilidad (Engineering Handbook) P2/P3 (Architecture Handbook)

Single Source of Truth

Todo dato con identidad propia tiene un único propietario que puede escribirlo — nunca "cualquiera con acceso puede escribirlo" (Domain Model Handbook, 08, Aggregate Roots). Sin un propietario claro, dos escritores concurrentes producen estados contradictorios sin que ninguno sea "el correcto". Cada tabla de este documento (03) declara explícitamente quién la escribe y quién solo la lee — nunca se asume. "Propietario" no es necesariamente quien se beneficia del dato: un Usuario es dueño de su propio Perfil, pero no es el único escritor de nivel_actual — ese campo lo escribe el proceso de Diagnóstico/Progresión en su nombre (Domain Model Handbook, DX-04). Ownership y "de quién es la información" son preguntas distintas.

Normalización

BREY normaliza solo cuando algo dentro de un campo necesita su propio índice o FK — nunca por pureza relacional a priori (ENG-ADR-05). workouts.ejercicios y workout_logs.ejercicios son jsonb, no tablas de Slots/Series normalizadas, porque ninguna consulta real filtra hoy por un campo dentro de ellas. La señal de normalizar ya está definida de antemano: el día que el tracking de PRs se vuelva una consulta real (MAX(peso) por ejercicio en el tiempo), se normaliza a tabla de series — nunca antes (Architecture Handbook, 10). Este documento no normaliza especulativamente ninguna estructura jsonb existente (04).

Integridad

Ninguna decisión de negocio se registra sin su razón (Architecture Handbook, P2) — todo agregado de tipo "decisión" (EventoProgresión) declara un campo de razón obligatorio, no opcional, como parte de su forma (07, 08). Un registro sin razón es una caja negra: no permite auditar, depurar, ni explicarle al usuario por qué el sistema decidió algo. La integridad referencial (FK) y los CHECK de vocabulario cerrado (07) son la forma en que este principio se hace cumplir por la propia base de datos, no solo por convención de código.

Persistencia vs. cache

BREY no tiene cache en ningún punto del sistema hoy — cero ISR, cero revalidate, cero memoización (Engineering Handbook, 09). El caso más relevante para este documento es el Reporte del BCS: se computa on-demand en cada visualización y nunca se persiste independientemente de sus Mediciones fuente (BCS Handbook, IN-D3; formalizado en Domain Model Handbook, DM-ADR-08) — para que nunca pueda quedar desactualizado respecto a una corrección de Medición. Cachear el Reporte es una optimización de infraestructura válida el día que el volumen lo justifique (BCS Handbook, 12: "cientos de Mediciones" proyectadas) — pero cachear no es persistir, y este documento no confunde ambos: un cache es descartable sin pérdida de información; una tabla no lo es.

Persistencia vs. evento

El estado de un Usuario es un puntero materializado (profiles.sistema_actual, nivel_actual) para lectura barata; el porqué de cómo llegó ahí vive en el historial de eventos (progression_events), nunca solo en uno de los dos (Motor BPS Handbook, MBPS-ADR-01). Event Sourcing puro — reconstruir el estado desde cero en cada lectura — fue evaluado y descartado por su costo sin beneficio adicional sobre este híbrido. Ante divergencia entre el puntero y el log de eventos, el log gana (IN-5, replay determinista) — el puntero es una optimización de lectura, nunca la fuente de verdad.

Persistencia vs. estado

La pregunta "¿en qué estado está esto ahora?" se responde con una lectura barata del puntero materializado — nunca recorriendo todo el historial de eventos en cada request. Pero el estado nunca es la única verdad persistida: cada transición de la máquina de estados de un Usuario (Motor BPS Handbook, 05) o de un Cliente/Medición/EnlacePúblico (Domain Model Handbook, 10) queda registrada como el evento que la causó — de modo que el estado actual sea siempre recomputable desde cero si el puntero llegara a corromperse (Motor BPS Handbook, pseudocódigo recomputarEstado). Un estado sin el evento que lo originó es, por definición, un estado sin auditoría — nunca válido en este ecosistema (08).
