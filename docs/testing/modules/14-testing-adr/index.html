Módulo 14 · Gobernanza

Testing ADR

Doce decisiones. La primera cierra AR-024. Las dos siguientes tratan AR-025, AR-026 y AR-013 exactamente como se pidió: documentadas, nunca resueltas mediante un cambio funcional.

Aceptada TEST-ADR-01

Este handbook cierra AR-024 documentalmente — la ejecución permanece en 0%

Contexto: AR-024 (Architecture Review) encontró que ninguna de las 39 reglas de Progression Engine, 15 transiciones de Motor BPS, o 25 tipos de evento tiene verificación ejecutable — porque no existe test runner ni lógica implementada.

Problema: AR-024 podría interpretarse como que solo se cierra escribiendo tests reales — pero eso requeriría motores implementados que hoy no existen, y este documento no implementa nada.

Alternativas consideradas: (a) declarar AR-024 sin cambios hasta que exista implementación real; (b) cerrar la mitad especificable de AR-024 — el plan completo de qué probar, en qué nivel, con qué caso — dejando explícito que la ejecución (0% de cobertura real) no cambia con este documento.

Decisión: se adopta (b). AR-024 se cierra en su dimensión de especificación: las once matrices de 04-12 cubren el 100% de las reglas/transiciones/endpoints ya documentados (13). La cobertura de código sigue siendo 0% — este documento no la cambia, solo elimina la excusa de "no sabíamos qué probar".

Consecuencias: el día que se implemente el primer motor real, el plan de pruebas ya existe completo — la única deuda pendiente es de ejecución, no de diseño.

Aceptada TEST-ADR-02

AR-025 se cierra indirectamente — la ambigüedad que lo motivaba ya no existe

Contexto: AR-025 advertía que cualquier mock del Veredicto de Recovery heredaría la ambigüedad de AR-001 (dos formas incompatibles entre Motor BPS Handbook y Progression Engine Handbook).

Problema: este documento necesita especificar cómo mockear el Veredicto sin reabrir esa ambigüedad ni inventar una tercera forma.

Alternativas consideradas: (a) documentar ambas formas históricas como igualmente válidas para mock, dejando la elección a cada implementador; (b) usar la forma ya reconciliada por un documento de mayor autoridad, citándola, no redecidiéndola.

Decisión: se adopta (b) — todo mock de Veredicto de Recovery de este documento (06) usa {procede, subtipo?, razon}, la forma canónica ya adoptada por API Contract Handbook (08, API-ADR-02). AR-025 queda cerrado como consecuencia directa de que su causa raíz (AR-001) ya tiene resolución aceptada — no porque este documento haya resuelto nada nuevo.

Consecuencias: ningún test futuro que siga este documento puede "heredar" la ambigüedad original, porque nunca la usa como referencia.

Aceptada TEST-ADR-03

AR-026 y AR-013 permanecen abiertos — se documenta el requisito de testing, no se inventa el esquema

Contexto: AR-013/AR-026 señalan que contexto (jsonb) no tiene esquema definido por tipo de evento, lo que impide verificar el replay determinista de forma completa.

Problema: el encargo de este handbook exige especificar Event Testing — pero sin esquema de contexto, una parte de esa especificación no puede completarse sin inventar información que ningún handbook de dominio ha decidido.

Alternativas consideradas: (a) inventar un esquema mínimo de contexto para poder especificar el test completo; (b) especificar exactamente qué se podrá probar el día que el esquema exista, marcando el caso como bloqueado mientras tanto.

Decisión: se adopta (b) — 08 lista tres casos concretos bloqueados por este gap, ninguno inventa la forma de contexto. AR-026/AR-013 quedan exactamente donde estaban: documentados, sin resolver, con su implicación de testing ahora explícita.

Consecuencias: el día que Progression Engine Handbook u otro documento de dominio defina el esquema de contexto, los tres casos de 08 pasan de bloqueado a especificables sin reescribir este documento — solo cambia su estado.

Aceptada — cita Engineering Handbook, 10 TEST-ADR-04

Integration nunca mockea Supabase completo, en ninguna superficie

Contexto: Engineering Handbook (10) ya decidió esta regla para motores; este documento la extiende a Database Testing (09) y API Testing (10 de este documento).

Problema: sin extender la regla explícitamente, alguien podría mockear Supabase para probar un endpoint "más rápido", perdiendo exactamente la cobertura de RLS que el nivel Integration existe para dar.

Alternativas consideradas: ninguna nueva — se aplica el criterio ya decidido a todas las superficies que lo necesitan.

Decisión: todo test integration de este documento, sin excepción de superficie, corre contra una base de datos Supabase de test real (02).

Consecuencias: un mock de Supabase en un PR de test de integración se rechaza en revisión, con la misma severidad que un UPDATE directo sobre historial (12).

Aceptada TEST-ADR-05

Sin objetivo numérico de cobertura de código — cobertura de especificación en su lugar

Contexto: Engineering Handbook (10) ya rechazó un porcentaje global de cobertura de código a favor de cobertura dirigida a motores de decisión.

Problema: "cobertura dirigida" sin una forma de medirla es una intención, no una métrica.

Alternativas consideradas: (a) fijar un porcentaje arbitrario igual (ej. 80% en motores); (b) medir cobertura de especificación — cuántas reglas/transiciones/endpoints ya documentados tienen un caso trazado en este handbook.

Decisión: se adopta (b) — 13 formaliza la métrica y reporta el estado actual por catálogo fuente.

Consecuencias: la métrica de este documento nunca baja por razones de código (no hay código) — solo puede bajar si un handbook de dominio agrega una regla nueva sin su caso correspondiente aquí.

Aceptada TEST-ADR-06

Un caso bloqueado se documenta explícitamente, nunca se omite ni se simula

Contexto: varios casos de este documento (el CHECK de 11 tipos de evento pendientes, M2; el esquema de contexto) no pueden ejecutarse hoy por brechas en otros handbooks.

Problema: omitir estos casos silenciosamente dejaría huecos invisibles en la cobertura de especificación (13); simularlos contra un estado hipotético (ej. asumir que M2 ya se aplicó) produciría un test que no refleja la realidad.

Alternativas consideradas: (a) omitir sin mención; (b) simular el estado deseado; (c) marcar explícitamente bloqueado con la razón exacta.

Decisión: se adopta (c), aplicada consistentemente en 08 y 09.

Consecuencias: cualquier lector de este documento ve exactamente qué está pendiente de otro handbook, sin necesidad de buscarlo por separado.

Aceptada · resuelta en Sprint 0 TEST-ADR-07

El test de RLS de workouts/workout_logs se especifica contra el estado correcto, no el real

Contexto: AR-018 (Architecture Review) documentaba que la política real de workouts/workout_logs permitía DELETE, contradiciendo la inmutabilidad exigida.

Problema: un test que verificara "el DELETE está permitido" describiría fielmente el estado de entonces, pero congelaría una brecha de seguridad conocida como si fuera el comportamiento deseado.

Alternativas consideradas: (a) especificar el test contra el estado real (permisivo) para que "pasara" en ese momento; (b) especificarlo contra el estado correcto (sin DELETE) para que fallara visiblemente hasta que la migración M1 se aplicara.

Decisión: se adoptó (b) — 09 lo declaraba explícitamente como el único caso de este documento que se esperaba roto hasta que otro artefacto (la migración M1) cambiara.

Consecuencias: el test funcionó como recordatorio ejecutable de una deuda de seguridad ya priorizada (IMP-ADR-04). Actualización Sprint 0: M1 se aplicó (supabase/schema.sql, supabase/migration_rls_endurecimiento.sql) — el caso de 09 ya no se especifica contra un estado pendiente, sino contra el estado real vigente. Esta decisión se conserva como registro de por qué nunca se escribió el test contra el estado permisivo mientras existió.

Aceptada TEST-ADR-08

Las 39 reglas de Progression Engine se prueban por categoría, con tres excepciones individuales

Contexto: las 39 reglas ya tienen "ejemplo válido"/"ejemplo inválido" en su propio handbook — transcribirlas una por una aquí sería duplicación, no especificación de testing nueva.

Problema: una matriz puramente por categoría (5 filas) podría ocultar que tres reglas (PE-012, PE-016, PE-018) tienen matices ya señalados por la Architecture Review que merecen tratamiento propio.

Alternativas consideradas: (a) matriz por categoría únicamente; (b) matriz por categoría más callouts individuales para las tres reglas con hallazgos propios de AR.

Decisión: se adopta (b) — 06 tiene la matriz de 5 categorías más un callout dedicado a PE-012 (AR-008, desempate sin operacionalizar).

Consecuencias: la cobertura de especificación (13) cuenta las 39 como cubiertas por categoría, sin fingir que las 36 restantes tienen menos detalle del que su propio handbook ya provee.

Aceptada TEST-ADR-09

Ningún caso de este documento fija una interpretación no decidida por su handbook de origen

Contexto: PE-012 usa "menor magnitud de cambio" como criterio de desempate sin operacionalizar entre unidades heterogéneas (AR-008, no resuelto).

Problema: especificar un test de PE-012 exige, en apariencia, decidir cómo se compara "1 repetición" con "2.5 kg" — algo que Progression Engine Handbook mismo no ha decidido.

Alternativas consideradas: (a) elegir un criterio de comparación razonable para poder escribir el caso completo; (b) especificar que el test debe declarar explícitamente qué criterio usa la implementación bajo prueba, marcado bloqueado hasta que el handbook de origen decida.

Decisión: se adopta (b), consistente con TEST-ADR-06.

Consecuencias: este documento nunca es la fuente de una decisión de negocio disfrazada de "solo es para el test".

Aceptada TEST-ADR-10

Los endpoints internos (Progression Engine, Recovery Engine) se prueban igual que los públicos

Contexto: API Contract Handbook (07) documenta POST /progression-engine/evaluar y POST /recovery-engine/evaluar como contratos reales, aunque el frontend nunca los invoque directamente.

Problema: podría asumirse que un endpoint "interno" necesita menos rigor de prueba que uno público.

Alternativas consideradas: (a) tratar los endpoints internos con menor prioridad de test; (b) tratarlos con el mismo rigor, más una prueba adicional de que la ruta de invocación indebida (UI→motor directo) está bloqueada.

Decisión: se adopta (b) — 10 de este documento no distingue rigor por visibilidad del endpoint, solo añade el caso de frontera correspondiente (05).

Consecuencias: un contrato interno mal probado fallaría exactamente igual de silencioso que uno público — este documento no acepta esa asimetría de riesgo.

Aceptada TEST-ADR-11

Todo caso de test se nombra por el ID de la regla/transición/constraint que verifica

Contexto: 03 ya establece esta convención de naming.

Problema: sin forzar esta trazabilidad por nombre, la matriz de cobertura de especificación (13) requeriría inspeccionar el contenido de cada test para saber qué cubre, no solo su nombre.

Alternativas consideradas: (a) nombres descriptivos libres; (b) nombres que citan el ID exacto de la regla de origen.

Decisión: se adopta (b), formalizada aquí como decisión de gobernanza, no solo de estilo.

Consecuencias: la matriz Regla→Test de 13 puede, en principio, generarse por herramienta a partir de los nombres de archivo/caso reales, el día que existan.

Aceptada TEST-ADR-12

Recovery Engine se prueba solo en su forma, nunca en su corrección fisiológica

Contexto: Recovery Engine tiene únicamente un contrato mínimo (IMP-ADR-01/02, citado desde API Contract Handbook) — su lógica de decisión real (qué constituye fatiga) no existe (AR-006).

Problema: un test que pareciera verificar "la decisión de fatiga es correcta" daría una falsa sensación de cobertura sobre algo que ni siquiera está especificado todavía.

Alternativas consideradas: (a) escribir casos que asuman una lógica de fatiga razonable para poder probar "algo"; (b) limitar los casos estrictamente a la forma del contrato (06), declarando explícitamente que la corrección de la decisión queda fuera de alcance hasta que exista un Recovery Engine Handbook.

Decisión: se adopta (b).

Consecuencias: cuando el Recovery Engine Handbook exista, este documento se extiende con los casos de lógica real — hasta entonces, la cobertura de "Recovery" en 13 se limita honestamente a forma de contrato, nunca a decisión de negocio inexistente.
