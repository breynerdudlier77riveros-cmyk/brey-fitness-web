Semántica de equipment — decisión fijada

equipment es conjuntivo: enumera el equipo imprescindible para ejecutar el ejercicio. Un ejercicio es elegible solo si todos los elementos de su lista están disponibles en el contexto del usuario. Un movimiento que puede ejecutarse con implementos alternativos se modela como entradas distintas relacionadas como variantes, no como una lista disyuntiva.

risk_zones — el campo de seguridad

Zonas (6): rodilla · cadera · lumbar · hombro · codo-muneca · tobillo. Intensidad (3): alto · medio · bajo.

Los tres estados posibles del campo tienen significados distintos y no intercambiables:

  • null — no evaluado. La entrada no es elegible para ningún usuario con zonas declaradas.
  • [] — evaluado: no carga ninguna zona en riesgo. Es una afirmación positiva.
  • [{zone, intensity}, …] — evaluado, con las cargas declaradas.

Ante duda sobre una intensidad, el valor correcto es no publicar el campo — nunca elegir el valor intermedio, que es el permisivo.

load_type — cómo progresa el ejercicio

type: external_load (progresa añadiendo carga) · bodyweight_pattern (progresa avanzando en dificultad de patrón) · isometric_hold (progresa en tiempo).
accepts_added_load: booleano — si el ejercicio admite lastre además de su progresión natural.

Este campo resuelve la bifurcación que el motor de progresión necesita y que ningún atributo anterior expresaba: distinguir progresión por carga de progresión por dificultad, y saber si un ejercicio en tope de cadena todavía admite carga añadida.

Invariante del bloque de Contenido

Ningún proceso automático interpreta estos seis campos. Son canal humano→humano. Si un consumidor necesitara un dato que solo aparece aquí, el dato falta en el bloque de Clasificación y debe añadirse allí mediante versión mayor — nunca extraerse de este texto.

La única excepción es search_terms, que alimenta búsqueda de usuario: su resultado nunca determina una decisión del sistema.

Por qué existen ya si no se pueblan

Reservar los tres campos ahora evita que añadir media en el futuro requiera una versión mayor del dataset. Su forma está fijada; su contenido llegará. Es la aplicación directa de DS-04: anticipar la extensión previsible es lo que permite congelar el modelo.

revisions — el historial es append-only

Cada entrada del array registra: número de revisión, fecha, autor, type (major · minor · fix) y reason en texto. Una entrada de revisión nunca se edita ni se elimina. Corregir un registro erróneo significa añadir una revisión nueva que lo explique.

Extensión de vocabularios

Regla de extensión aditiva

Añadir un valor a un enumerado no es una versión mayor si la operación es puramente aditiva: las entradas existentes siguen siendo válidas y ningún consumidor deja de funcionar. Requiere: versión menor del dataset, registro del motivo y confirmación de que ninguna proyección asume la lista cerrada anterior.

Eliminar o renombrar un valor de un enumerado sí es versión mayor: invalida entradas existentes.
