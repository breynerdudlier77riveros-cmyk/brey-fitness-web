Flujo de una request típica

De la carga de página a la respuesta
sequenceDiagram
  participant U as Usuario
  participant PX as proxy.ts
  participant SC as Server Component
  participant SA as Server Action
  participant REPO as Repositorio
  participant PG as Postgres (RLS)
  U->>PX: GET /app/perfil
  PX->>PX: revalida sesión (UX, no seguridad real)
  PX-->>U: continúa o redirige a /login
  U->>SC: renderiza página
  SC->>REPO: getProfile(supabase, userId)
  REPO->>PG: select * from profiles (RLS evalúa)
  PG-->>REPO: fila o vacío
  REPO-->>SC: Profile mapeado
  U->>SA: submit de formulario
  SA->>REPO: updateProfile(supabase, userId, patch)
  REPO->>PG: update ... where id = userId (RLS evalúa)

Invariantes de arquitectura

  • IN-E1: el Domain nunca importa de Next.js, React ni Supabase — es portable por definición (FT-13).
  • IN-E2: toda escritura a Supabase pasa por un repositorio (04) — ningún componente de Frontend llama supabase.from() directamente, salvo la excepción documentada de Navbar.tsx (04).
  • IN-E3: la seguridad real nunca depende únicamente de la capa de Application — RLS (08) es la barrera final incluso si Application tiene un bug.
  • IN-E4: ningún bounded context futuro se construye sin antes tener su propio handbook de dominio (00, 15).
