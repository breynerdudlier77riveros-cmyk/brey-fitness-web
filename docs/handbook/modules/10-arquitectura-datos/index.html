Arquitectura de Datos

El modelo completo: las 5 tablas que existen en producción (documentadas fielmente, no idealizadas), la tabla nueva requerida (progression_events), las formas de los jsonb, índices, políticas RLS, y la política de versionado y migraciones. Cada entidad se clasifica primero en su categoría (P9) — eso decide quién la escribe.

Extensión requerida — zonas estructuradas

El filtro por zona de riesgo (04) exige zonas_riesgo jsonb (lista de slugs de zona declarados por el usuario) + las restricciones temporales por dolor (06) que viven como eventos. lesiones texto libre NO se parsea jamás (invariante de Notas, 03). Migración pendiente — Roadmap v1.

Limitación RLS documentada (heredada, sin resolver)

La política de UPDATE de profiles permite editar cualquier columna propia — incluidas sistema_actual/nivel_actual. Inofensivo mientras no haya permisos comerciales atados; cuando la Regla de Activación se implemente de verdad, esas dos columnas deben escribirse por camino de servidor con autorización propia, no por la política general. Registrado también en el archivo real de esquema.

workouts — sesión instanciada

Columnas existentes: id uuid PK · user_id FK not null · system_slug FK · nombre text not null · semana/semana_total int · fecha_planificada date not null · duracion_estimada_min int · ejercicios jsonb not null default '[]' · estado text check ∈ {planificado, completado, perdido} · created_at. Sin fila = descanso; "hoy" se calcula, nunca se persiste.

Forma requerida del jsonb ejercicios (v-Generator)

Array de slots, cada uno: { patron, rol, ejercicio: {slug, nombre, modalidad}, series, reps: {min, max} | duracion_s, rpe_objetivo, descanso_s, tempo?, notas? } — todo desnormalizado (P5/I-G2). La forma actual (EjercicioPlan: nombre/series/reps/peso/intensidad) es la precursora; la migración de forma es aditiva y solo afecta filas nuevas (las viejas no existen: la tabla está vacía).

workout_logs — historial de ejecución

Columnas existentes: id uuid PK · user_id FK not null · workout_id uuid FK → workouts on delete set null (sesiones ad-hoc permitidas) · fecha date not null · duracion_real_min int · volumen_total_kg numeric ⚠ · ejercicios jsonb · completado boolean · created_at.

Forma requerida del jsonb ejercicios (v-Player)

Array por ejercicio ejecutado: { ejercicio_slug, nombre, sustituido_desde?, series: [{n, peso_kg, reps | duracion_s, rpe, timestamp}], omitido?, motivo_omision? }. La fila se inserta UNA VEZ al cierre de sesión (I-W3) — por eso las políticas no necesitan UPDATE: la corrección pre-cierre ocurre en la cola local del Player, y la post-cierre será un evento nuevo (v2).

Migración de endurecimiento aplicada — Sprint 0

Las políticas originales de workouts/workout_logs eran "CRUD propio" (for all) — más permisivas de lo que P3 exige. Aplicado: workout_logs → solo select+insert propios; workouts → select+insert propios + update propio (transición de estado; RLS de Postgres no restringe por columna — la disciplina de "solo estado" sigue siendo de capa de aplicación, documentada). El delete desapareció de ambas (supabase/schema.sql, supabase/migration_rls_endurecimiento.sql).

Capa de coerción — la trampa de PostgREST

Regla vigente (ya implementada — ADR-007)

PostgREST serializa numeric como string JSON (para no perder precisión); int llega como número real. Columnas afectadas: precio, peso_kg, altura_cm, volumen_total_kg. Todo acceso pasa por la capa de repositorios+mappers, y numOrNull() es el ÚNICO punto de coerción del sistema. Un Number(row.x) fuera de los mappers es un defecto. Este bug existió de verdad (una suma que concatenaba strings en el agregado de progreso) — la capa existe porque el riesgo es real, no teórico.

Versionado y migraciones — política

  • Patrón establecido (real, en uso): archivos migration_*.sql planos e idempotentes — ADD COLUMN IF NOT EXISTS; para constraints (sin IF NOT EXISTS nativo), bloque DO $$ verificando pg_constraint por conname + conrelid. Cada archivo puede pegarse N veces sin error.
  • schema.sql paralelo: el estado completo para instalación desde cero, actualizado en el mismo cambio que cada migración. Producción solo recibe migraciones; schema.sql nunca se re-pega sobre datos.
  • Catálogo en código: versionado por git; el evento semana_generada registra la versión de catálogo usada — es lo que hace reproducible una generación pasada (P1) sin snapshot de DB.
  • Evolución de formas jsonb: aditiva con campo v discriminador cuando cambie la forma; los mappers leen todas las versiones históricas, escriben solo la vigente (P3: lo escrito no se migra en masa).

Riesgos, deuda y extensiones

Deuda — sin tipos generados de Supabase

Los mappers son casts manuales centralizados: cada columna nueva exige tocar SQL + migración + tipos + mapper (4 lugares, a mano). supabase gen types eliminaría una clase de error — candidata v1/v2, registrada.

Deuda — jsonb vs. tabla normalizada de series

Trade-off heredado y documentado en el esquema real: ejercicios es jsonb. El disparador de normalización ya está definido: cuando el tracking de PRs se vuelva consulta real (MAX(peso) por ejercicio en el tiempo), se normaliza a tabla de series. Antes no.

Extensión — plantillas a DB

Cuando el equipo de contenido necesite editar sin deploy, las plantillas migran de código a tablas — el contrato de los mappers no cambia (ADR-009 prevé la transición).
