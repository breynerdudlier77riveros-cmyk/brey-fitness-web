Módulo 15 · Gobernanza

API-ADR

Diez decisiones propias de este documento — todas de notación, consolidación o documentación de gaps ya existentes. Ninguna redefine una regla de negocio de los nueve handbooks que este documento respeta; donde una discrepancia real existía, se cita quién ya la resolvió (jerarquía, 00) o se declara sin resolver.

Aceptada API-ADR-01

Notación REST transporte-agnóstica para todo el catálogo

Contexto: el Engineering Handbook (06) afirma que BREY no expone una API pública versionada — sus contratos reales son firmas de repositorio, Server Actions y 2 Route Handlers. El encargo de este documento exige, en cambio, un catálogo con ruta y método HTTP por operación.

Problema: documentar cada operación como si ya fuera un endpoint HTTP real podría leerse como una afirmación de que BREY va a exponer una API pública — algo que ningún handbook decide todavía.

Alternativas consideradas: (a) documentar solo las firmas de función ya usadas por Server Actions/repositorios, sin ruta ni método; (b) usar ruta + método como notación transporte-agnóstica, igual que el BCS Handbook (13) ya hace con pseudocódigo.

Decisión: se adopta (b). Cada fila del catálogo (07) es una unidad de contrato — quién la invoca, qué recibe, qué devuelve — independiente de si hoy se realiza como Server Action, Route Handler, o mañana como endpoint de una API pública.

Consecuencias: este documento nunca afirma que BREY expone hoy una API HTTP pública — lo aclara explícitamente en 00 y 01. Una implementación futura puede materializar cualquier fila como Server Action sin contradecir este documento.

Aceptada API-ADR-02

Forma canónica del Veredicto de Recovery — se adopta la ya resuelta por IMP-ADR-01

Contexto: la Architecture Review (AR-001) encontró formas incompatibles del mismo DTO entre Motor BPS Handbook ({si, tipo?, razon?}) y Progression Engine Handbook ({procede, tipo, razon}). El Implementation Handbook (IMP-ADR-01), de mayor autoridad que este documento (00), ya reconcilió ambas en {procede: boolean, subtipo?: "programada"|"reactiva", razon: string}.

Problema: este documento necesita una única forma para el catálogo (07, 08) sin volver a arbitrar algo ya arbitrado por un documento superior.

Alternativas consideradas: (a) re-arbitrar la discrepancia de forma independiente; (b) adoptar literalmente la forma ya fijada por IMP-ADR-01, sin modificarla.

Decisión: se adopta (b). Este documento nunca decide una forma de DTO donde el Implementation Handbook ya decidió una.

Consecuencias: el catálogo (07) y los DTO (08) usan {procede, subtipo?, razon} en todo lugar donde aparece el Veredicto de Recovery. Motor BPS Handbook, Progression Engine Handbook y el módulo de Recovery Engine del Architecture Handbook siguen mostrando sus formas originales, sin editar — este documento no las sustituye, solo no las usa como contrato de implementación.

Aceptada API-ADR-03

CHECK de progression_events.tipo — se documenta el consolidado de 25, pendiente de migración

Contexto: el CHECK real de progression_events.tipo tiene 14 valores; Motor BPS Handbook y Progression Engine Handbook, entre ambos, requieren 11 valores adicionales ya identificados por el Engineering Handbook (07) y el Domain Model Handbook (11) — 25 en total.

Problema: el catálogo (07) y el DTO de Evento (08) necesitan listar qué eventos puede producir cada endpoint — pero solo 14 de esos 25 valores existen hoy en la base de datos real.

Alternativas consideradas: (a) documentar solo los 14 valores reales, dejando fuera del catálogo la funcionalidad ya especificada por Motor BPS/Progression Engine; (b) documentar los 25 consolidados, marcando explícitamente que 11 dependen de la migración M2 (Implementation Handbook, 05) todavía no aplicada.

Decisión: se adopta (b). El catálogo (07) y el DTO de Evento (08) listan los 25 valores; este ADR es la referencia única de que 11 de ellos no son insertables hasta que M2 se aplique.

Consecuencias: un endpoint que "produce" escalon_avanzado hoy fallaría contra la base de datos real con un error de CHECK — comportamiento esperado y ya cubierto por el propio catálogo de errores (09, "tipo fuera del CHECK") hasta que M2 se aplique.

Aceptada API-ADR-04

origen = 'coach' permanece reservado, sin evento ni endpoint inventado

Contexto: el CHECK de progression_events.origen incluye coach sin que ningún tipo de evento lo use como productor (AR-011) — una extensión especulativa para un futuro Coach IA que no tiene handbook de dominio.

Problema: el DTO de Evento (08) necesita listar el CHECK completo de origen, lo que expone este valor sin contenido.

Alternativas consideradas: (a) omitir coach de la tabla para no exponer un vacío; (b) listarlo explícitamente marcado como reservado sin evento asociado.

Decisión: se adopta (b). Ocultar el valor sería menos honesto que documentar la reserva tal como es.

Consecuencias: ningún endpoint de este catálogo (07) tiene a Coach IA como actor. Si un Coach IA Handbook llega a existir, este documento se extiende entonces — no antes.

Aceptada API-ADR-05

No existe un rol Admin — no se inventa en este documento

Contexto: el encargo original de este handbook nombra "trainer, cliente, admin, anonymous" como los roles a documentar en Autenticación (03). El Security Handbook (Engineering, 08) no define ningún rol de administrador transversal — solo Usuario, Entrenador (un Usuario en contexto BCS), Cliente y Anonymous.

Problema: documentar un rol Admin con permisos inventados llenaría el vacío que el encargo sugiere, pero violaría directamente la restricción de no inventar funcionalidad nueva.

Alternativas consideradas: (a) inventar un rol Admin razonable (ej. "puede ver todos los Entrenadores"); (b) documentar los cuatro actores reales y registrar la ausencia de Admin como pregunta abierta.

Decisión: se adopta (b) — ver 03 y 16 (AP-01).

Consecuencias: ningún endpoint del catálogo (07) tiene a "Admin" como actor. Si BREY necesita un rol de operación transversal en el futuro, requiere su propia decisión de producto antes de que este documento lo incorpore.

Aceptada API-ADR-06

Rate limiting — se documenta dónde importa, no cifras inventadas

Contexto: ni el Security Handbook ni el Performance Handbook (Engineering, 08/09) definen un límite numérico de rate limiting en ningún endpoint real.

Problema: el encargo pide explícitamente una sección de "límites, políticas, 429, reintentos" (12) — una tabla vacía se sentiría incompleta, pero llenarla con cifras plausibles sería inventar una política que nadie ha decidido.

Alternativas consideradas: (a) proponer cifras razonables (ej. 60 req/min) como punto de partida; (b) documentar la forma de la respuesta 429 (ya derivable de 06) y dónde el riesgo es mayor, sin cifras.

Decisión: se adopta (b).

Consecuencias: 12 tiene una Matriz Endpoint→Rate Limit completa en estructura, con la columna de límite numérico marcada "No definido" en cada fila — honesto sobre el estado real, sin fingir una decisión de producto que no existe.

Aceptada API-ADR-07

Sin convención de request ID / trace ID / correlation ID

Contexto: el Observability Handbook (Engineering, 11) declara explícitamente que no existe distributed tracing ni un identificador de request propagado — "añadiría complejidad sin un problema real que resolver todavía".

Problema: el encargo pide una sección de Observabilidad (14) que incluya request ID/trace ID/correlation ID — términos que ningún handbook define para este ecosistema.

Alternativas consideradas: (a) definir una convención nueva de header X-Request-Id propagado por todo el catálogo; (b) documentar honestamente la ausencia, con la convención real que sí existe ([contexto] en logs).

Decisión: se adopta (b).

Consecuencias: 14 documenta el gap explícitamente en vez de fabricar una convención. Se registra como pregunta abierta (AP-05, 16) para cuando el volumen de producción lo justifique.

Aceptada API-ADR-08

Idempotencia — se documentan claves reales, se declaran gaps donde no las hay

Contexto: algunas operaciones tienen clave de idempotencia real y ya especificada (transaccion_id, device_id+secuencia, SEMANA_YA_GENERADA); otras — la creación de Cliente/Medición/EnlacePúblico del BCS, el INSERT de un EventoProgresión — no tienen ninguna definida por ningún handbook (AR-027).

Problema: presentar el catálogo como si todo fuera idempotente ocultaría un riesgo real; presentar todo como no idempotente ignoraría lo que sí está resuelto.

Alternativas consideradas: (a) inventar una clave de idempotencia razonable para las operaciones sin definir (ej. hash del body); (b) documentar cada caso con su estado real: clave conocida, o gap explícito.

Decisión: se adopta (b) — 11 tiene dos tablas separadas, una por cada caso.

Consecuencias: un reintento de red sobre POST /bcs/clientes puede crear un Cliente duplicado hoy — riesgo real, documentado, no resuelto por este documento porque su resolución (ej. una clave de idempotencia por Entrenador+nombre+fecha) es una decisión de producto/dominio, no de contrato.

Aceptada API-ADR-09

PATCH de Medición no tiene semántica de reemplazo en sitio

Contexto: PATCH /bcs/mediciones/{id} (07) representa la corrección de una Medición (BCS Handbook, UC-06) — pero por IN-D1/IN-23 (Domain Model Handbook), una Medición vigente nunca se edita en sitio: la corrección anula la anterior y crea una nueva.

Problema: un consumidor familiarizado con la semántica estándar de PATCH (actualización parcial en sitio del mismo recurso) asumiría, incorrectamente, que el id de la respuesta es el mismo que el del path.

Alternativas consideradas: (a) modelar la corrección como POST /bcs/mediciones/{id}/corregir para evitar la ambigüedad de método; (b) mantener PATCH por ser semánticamente la operación más cercana (actualización parcial de valores), documentando la desviación explícitamente.

Decisión: se adopta (b) — PATCH describe mejor la intención del actor (corregir valores) que un sub-recurso de acción; la desviación se documenta en 07 y aquí, no se oculta.

Consecuencias: todo consumidor de este endpoint debe leer la respuesta para obtener el id vigente — nunca asumir que es el mismo que el del path.

Aceptada API-ADR-10

Paginación por rango de fecha/cursor — no offset/límite genérico

Contexto: el único umbral de paginación realmente especificado (BCS Handbook, 12: >50 Mediciones → 20 por página) es por fecha, no por offset numérico. Ningún otro handbook especifica paginación.

Problema: el encargo pide una convención general de paginación (05, 06) — sin un segundo precedente real que generalizar.

Alternativas consideradas: (a) adoptar OFFSET/LIMIT genérico, más común en APIs REST convencionales; (b) generalizar el único patrón real (cursor/rango de fecha) a cualquier lista futura del catálogo que lo necesite.

Decisión: se adopta (b) — es el único patrón con precedencia real en el ecosistema, y evita los problemas de consistencia de OFFSET/LIMIT sobre datos que crecen (Mediciones, WorkoutLogs, EventoProgresión).

Consecuencias: cualquier endpoint nuevo de este catálogo que necesite paginar adopta cursor/fecha_desde/fecha_hasta (05) en vez de page/per_page.
