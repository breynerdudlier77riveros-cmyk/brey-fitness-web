Decisiones de Arquitectura (ADR)

Las decisiones propias de este handbook (PE-ADR-01…06). Las decisiones heredadas del marco (ADR-003, ADR-005, ADR-010, ADR-012 del Architecture Handbook; BPS-007/019/022 del Motor BPS Handbook) no se re-registran aquí — se citan donde aplican.

Registro propio

Aceptada
PE-ADR-01

Precedencia explícita en vez de ponderación numérica

Contexto: el modelo de decisión (05) necesita un mecanismo para resolver conflictos entre reglas PE-XXX que compiten por la misma variable o el mismo ciclo.

Problema: un sistema de pesos numéricos permite expresar "casi cualquier cosa", pero vuelve el resultado de un conflicto impredecible sin ejecutar el sistema completo, y hace que ajustar un caso rompa silenciosamente otros.

Alternativas descartadas: ponderación por puntaje (indebugueable, no auditable por un humano en segundos); orden de ejecución del código como precedencia implícita (frágil ante refactors, invisible en la documentación).

Decisión: escalera de precedencia explícita de 5 niveles (05), documentada regla por regla en 07. 🟠 decisión de producto

Consecuencias: cada regla nueva debe declarar su nivel de precedencia antes de entrar al catálogo — no hay forma de añadir una regla "silenciosa" sin decidir dónde vive en la escalera.

Aceptada
PE-ADR-02

Track y Sistema fuera del alcance de macroprogresión

Contexto: el prompt original que originó este handbook pedía documentar "cuándo cambia... Track, Sistema" dentro de macroprogresión.

Problema: Track y Sistema ya están gobernados por la máquina de activación del Motor BPS Handbook (ADR-002/BPS-012) y por decisiones comerciales (compra) — construir aquí una segunda lógica de cambio duplicaría o contradiría esa autoridad, violando P4.

Alternativas descartadas: definir un umbral de rendimiento que "recomiende" cambio de Sistema (crearía una segunda fuente de verdad sobre activación, inevitablemente divergente de la primera con el tiempo).

Decisión: Track/Sistema quedan explícitamente fuera de este motor (PE-018, 09 "No alcance"); el Nivel máximo alcanzado produce "sostiene, en tope", nunca una recomendación de Sistema.

Consecuencias: resuelve una tensión real entre el prompt original y la arquitectura ya publicada — documentada aquí en vez de aplicada silenciosamente.

Aceptada
PE-ADR-03

Dolor, Fatiga y Sueño nunca se procesan directamente

Contexto: el prompt original pedía documentar cómo "Dolor, Fatiga, Sueño... intervienen" en la autorregulación de este motor.

Problema: interpretar estas señales exige criterio clínico/fisiológico que ya es responsabilidad exclusiva del Recovery Engine (P8, ADR-010 del marco) — procesarlas aquí también crearía dos intérpretes potencialmente contradictorios de la misma señal de seguridad.

Alternativas descartadas: que este motor las lea "solo como contexto adicional, sin decidir" (en la práctica es imposible trazar la línea entre "leer" y "decidir" una vez que la señal influye en cualquier salida).

Decisión: este motor solo recibe el Veredicto ya resuelto de Recovery (PE-023/024/025); nunca un campo crudo de dolor, fatiga o sueño.

Consecuencias: el Veredicto de Recovery se vuelve una entrada obligatoria y no nulable del contrato (04) — su ausencia es un error de invocación, nunca un caso de negocio de este motor.

Aceptada · marcada experimental
PE-ADR-04

Deload preventivo como mecanismo propio de este motor

Contexto: la escalera de acciones ante estancamiento confirmado (PE-031) necesita un segundo escalón antes de llegar al retroceso de eslabón.

Problema: no existe evidencia externa sobre si una descarga temprana ante estancamiento sostenido mejora el resultado más que simplemente seguir variando la prescripción.

Alternativas descartadas: omitir el mecanismo y saltar directo de "variar variable secundaria" a "retroceder eslabón" (intervención demasiado agresiva para una meseta que podría resolverse con descanso); copiar el criterio de deload reactivo de Recovery para este caso (mezclaría la autoridad de dos motores distintos).

Decisión: se introduce el deload preventivo (PE-035) como sugerencia NO vinculante, marcada explícitamente 🔴 hipótesis — a diferencia de todo lo demás en autorregulación, que es 🟠 o 🟡.

Consecuencias: requiere instrumentación específica (14) para validar o refutar la hipótesis con datos reales de producción antes de considerarlo para escalarlo a vinculante.

Aceptada
PE-ADR-05

Un único sistema de esfuerzo por Slot — RPE o RIR, nunca ambos

Contexto: el prompt pedía cubrir tanto "RPE objetivo" como "RIR" como variables independientes de microprogresión.

Problema: permitir que ambos sistemas convivan en el mismo Slot obliga a un árbitro adicional (¿cuál manda si contradicen?) sin ningún beneficio de programación claro.

Alternativas descartadas: permitir combinación libre con un árbitro de prioridad fijo (RPE siempre gana sobre RIR) — descartada por ser una complejidad añadida sin caso de uso real que la exija en v1.

Decisión: mutuamente excluyentes por Slot (PE-007/008, PE-019/020) — el programa elige uno u otro al definir el Slot.

Consecuencias: simplifica el árbitro de conflictos a costa de no soportar programas que mezclen ambos sistemas dentro de una misma sesión (19, pregunta abierta).

Aceptada · decisión propia
PE-ADR-06

Umbral de estancamiento: 3 apariciones consecutivas

Contexto: ningún handbook anterior fija un umbral de apariciones consecutivas para considerar confirmada una meseta de estancamiento — el concepto de "estancamiento" es propio de este motor, sin precedente en otro handbook.

Problema: sin una decisión explícita, cualquier valor (2, 3, 4…) parece igualmente arbitrario sin justificación documentada.

Alternativas descartadas: un umbral menor (2 apariciones) — descartado por sobre-reaccionar a variación normal de una sola sesión; un umbral mayor (4 o 5) — descartado por retrasar innecesariamente la detección de una meseta real.

Decisión: se fija en 3 apariciones consecutivas sin avance (PE-027), como decisión propia de este motor 🟠 decisión de producto.

Consecuencias: si un futuro handbook de Motor BPS introduce su propio concepto de estancamiento, debe citar este umbral en vez de definir uno independiente — para prevenir la inconsistencia numérica entre documentos que una decisión paralela sin coordinación produciría.
