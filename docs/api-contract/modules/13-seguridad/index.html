Seguridad

Cómo se aplica en la práctica lo que 03 declara — RLS por tabla, validación de entrada y salida, y manejo de secretos. Consolidado del Security Handbook (Engineering, 08) y la Architecture Review (AR-018, AR-019).

AR-018 — brecha real, todavía no cerrada

Las políticas actuales de workouts/workout_logs permiten DELETE por su dueño — más permisivo de lo que FT-09 (Inmutabilidad) exige. Un usuario puede borrar su propio historial de entrenamientos hoy. La migración de endurecimiento ya está especificada (Architecture Handbook, 10; Implementation Handbook, 05, M1: workout_logs → solo select+insert; workouts → select+insert+update, sin delete en ninguna) pero no aplicada. Este documento no puede declarar DELETE /workouts/{id} como parte del catálogo (07) porque ningún caso de uso de producto lo requiere — su ausencia del catálogo es intencional, no un olvido.

JWT — recordatorio

getUser(), nunca getSession() a solas, para decidir identidad (03). RLS es la barrera de última instancia — ninguna comprobación de ownership en la capa de aplicación sustituye una política de RLS ausente (ENG-ADR-04).

Validación de input — nunca confiar en el cliente

Toda regla de 05 se re-verifica en el servidor, incluso si la interfaz ya validó el mismo campo — la validación de cliente es UX, nunca seguridad. Ningún endpoint de este catálogo asume que un body ya viene válido porque proviene del propio frontend de BREY.

AR-019 — regla sin guardrail técnico

La regla "ningún secreto de servidor con prefijo NEXT_PUBLIC_" es hoy disciplina manual — no hay CI, lint rule ni secret-scanning que la haga cumplir (Security Handbook, Engineering 08/12). Este documento no inventa ese guardrail — lo hereda como riesgo abierto, condicionado a que SUPABASE_SERVICE_ROLE_KEY se active alguna vez.
