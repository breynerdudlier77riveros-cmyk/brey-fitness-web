Módulo 00 · Fundamentos

Introducción

Este documento responde exactamente una pregunta: ¿cómo se implementa BREY, paso por paso, sin que nadie tenga que tomar una decisión arquitectónica durante el desarrollo? No especifica dominio, no especifica diseño, no especifica arquitectura técnica — todo eso ya existe. Este documento orquesta.

Autoridad: handbook > código Orquesta 6 handbooks — no reescribe ninguno Sin código, sin TypeScript, sin SQL, sin React, sin Supabase

Objetivo

Que un equipo que nunca ha visto BREY pueda abrir este documento y saber, en cada momento, exactamente qué construir a continuación, en qué orden, con qué está bloqueado, y cuándo algo está listo para pasar a la siguiente etapa — sin tener que decidir nada que ya esté resuelto en otro documento.

Corrección Sprint 0 — documentos construidos después de este handbook

API Contract Handbook, Database Handbook y Testing Handbook se construyeron después de este documento, citándolo fielmente — no son entrada de este handbook, sino capas de detalle adicionales sobre las superficies de API, persistencia y verificación respectivamente. Se referencian aquí para que un lector de este documento sepa que existen: el orden de migraciones de 05 es la fuente que Database Handbook formaliza; los pasos de 06-09 son la fuente que API Contract Handbook y Testing Handbook formalizan. Ninguno de los tres contradice el orden ya fijado aquí.

Alcance

  • El orden exacto de construcción, migraciones, despliegue, integración, testing y validación.
  • Qué puede construirse en paralelo y qué no, y por qué (citando el documento de dominio que lo determina).
  • El estado de cada pieza del sistema en un momento dado (12).
  • Los checklists operativos que gobiernan cada Pull Request, Merge y Release (13).

Cómo leer este documento

Se reutiliza el sistema de tres etiquetas del Engineering Handbook para referenciar el estado de cualquier pieza citada de otro documento:

implementado especificado futuro

Y se introduce un segundo sistema, propio de este documento, para el estado de ejecución de cada pieza de trabajo (12) — distinto del anterior porque mide progreso de construcción, no estado de especificación:

no iniciado en progreso bloqueado implementado verificado

Regla absoluta

Prioridad de este documento

Si una implementación futura contradice este handbook, este handbook tiene prioridad. Esto no invalida a los seis documentos de dominio/diseño/ingeniería — este handbook nunca decide qué construir, solo en qué orden y bajo qué condición de entrada/salida. Cuando este documento y un handbook de dominio parecen contradecirse, la lectura correcta es que este documento está secuenciando, no redefiniendo.

Corrección Sprint 0 — rango frente a Architecture Review y Domain Model Handbook: este documento se subordina a la Architecture Review v1.0 (sus hallazgos 🔴/🟠 condicionan el Roadmap y el Orden de construcción, arriba) y precede al Domain Model Handbook, escrito después — frente a este último, el mismo principio aplica en ambas direcciones: el Domain Model Handbook gana en su propio terreno (lenguaje, entidades, ownership), este documento gana en el suyo (orden y condición de entrada/salida).
