Convenciones de Requests

Cómo se recibe una entrada en cualquier endpoint de este catálogo — query params, path params, body, y la frontera exacta entre "campo ausente" y "campo inválido".

Path params

Identifican el recurso direccionado por su id real (Aggregate Root, Domain Model Handbook 08) o por un identificador de negocio estable cuando el recurso es catálogo (slug de Sistema) o de acceso público (token de EnlacePúblico). Nunca se anida un path param de un contexto dentro de otro que el dominio no permite navegar — GET /clientes/{id}/workouts no existe porque esa navegación está explícitamente prohibida (Domain Model Handbook, 09; ver 02).

Path paramIdentificaEjemplo
{slug}Un Sistema del catálogo — estable, legible, nunca un UUIDGET /sistemas/{slug}
{id}Un Aggregate Root real — UUID (Workout, Cliente, Medición, EnlacePúblico, etc.)GET /bcs/clientes/{id}
{token}El token opaco de un EnlacePúblico — nunca el id interno del recurso (BCS Handbook, 10, IN-A2)GET /reportes/{token}

Query params

Filtran o acotan una Query — nunca cambian el efecto de una operación de escritura. La única convención de paginación real del ecosistema es por rango de fecha, no por offset/límite genérico (Performance Handbook, Engineering 09; BCS Handbook, 12 — ver 06 para el DTO de paginación).

Query paramUsoEjemplo
fecha_desde, fecha_hastaAcotar una lista por rango de fecha — reemplaza getXEnRango de la capa de repositorioGET /workouts?fecha_desde=2026-07-01&fecha_hasta=2026-07-31
tipo, origenFiltrar el timeline de progression_events por el CHECK de tipo/origen (09-domain-events, Engineering)GET /motor-bps/eventos?origen=recovery_engine
cursorContinuación de paginación cuando el volumen supera el umbral especificado (BCS Handbook, 12: >50 Mediciones)GET /bcs/clientes/{id}/mediciones?cursor=…
estadoFiltrar por estado de máquina cuando el recurso lo tiene (ej. Clientes activos vs. archivados)GET /bcs/clientes?estado=activo

Body

JSON, snake_case (01). Todo body de escritura corresponde a un Input DTO nombrado en 08 — nunca un objeto ad-hoc definido solo dentro de un endpoint. Un DTO de entrada nunca es idéntico al DTO de salida del mismo recurso: acepta solo los campos que el actor puede fijar, nunca campos gestionados por el sistema (id, created_at, estado derivado) — regla ya real en ProfileUpdateInput frente a Profile (Engineering Handbook, 06).

Validación — dos capas, dos catálogos de error distintos

CapaQué validaStatus
Forma (sintáctica)JSON parseable, tipos básicos correctos, campos obligatorios presentes400
Regla de negocio (semántica)Rangos físicos válidos (Medición), gates de Perfil completos, transición de estado permitida422 o 409 según el caso — ver 09

La ausencia de un campo opcional nunca es un error — es un caso de negocio explícito (ej. Prescripción nula para un Slot nuevo no es ENTRADA_INVALIDA, Motor BPS Handbook, 03). Confundir "ausente" con "inválido" es exactamente el error que el propio Motor BPS Handbook corrige con su regla V-2.

Campos opcionales vs. obligatorios — cómo se documentan

En las tablas de DTO (08), un campo obligatorio se lista sin marca; uno opcional se marca con ? tras su nombre, siguiendo la misma notación ya usada en los DTO originales de Motor BPS Handbook y Architecture Handbook (ej. {si, tipo?: programada|reactiva, razon?}). Un campo puede ser condicionalmente obligatorio (obligatorio solo si otro campo tiene cierto valor) — esos casos se documentan en prosa junto al DTO, nunca solo con la notación ?, para no perder la condición.

Naming — consistencia con el dominio

Todo campo de un body de request usa exactamente el término del Lenguaje Ubicuo (Domain Model Handbook, 01) que le corresponde — nunca un sinónimo prohibido. Un request de Diagnóstico nunca llama quiz a lo que el dominio llama Diagnóstico; un request de BCS nunca llama usuario a lo que el dominio llama Cliente (el error de lenguaje que el propio Domain Model Handbook califica como "el más peligroso del ecosistema").
