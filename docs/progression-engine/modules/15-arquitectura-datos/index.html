Arquitectura de Datos

El contrato conceptual que la persistencia debe soportar — no un esquema SQL (fuera de alcance por restricción explícita), sino la forma exacta de lo que el Motor BPS debe guardar en nombre de este motor.

Objetivo

Que quien diseñe el esquema físico tenga cada campo, cada relación y cada invariante de datos ya decidido — solo falta traducir a DDL.

Alcance

Prescripción vigente por Slot, puntero de posición en jerarquía, y el registro de eventos de decisión con su contexto completo.

No alcance

DDL, tipos de columna concretos, índices, políticas de RLS — decisiones de implementación que pertenecen al equipo de ingeniería, no a este documento de dominio.

Campos de Prescripción vigente

Las 10 variables ya listadas en el módulo 08 — nulables individualmente según lo que el Slot use, nunca nulables como registro completo (03, IN-M2).

Eventos — extensión requerida sobre el marco existente

Hallazgo de consistencia — mismo patrón que el detectado en el Motor BPS Handbook

Los tipos de evento introducidos en el módulo 13 de este documento (prescripcion_actualizada, escalon_avanzado, escalon_retrocedido, estancamiento_confirmado, estancamiento_resuelto, deload_aplicado, deload_cancelado, conflicto_resuelto, error_invocacion) no existen en la lista CHECK de progression_events definida en el Architecture Handbook (módulo 10), la cual ya requería extensión aditiva por el hallazgo previo del Motor BPS Handbook (gate_fallado, transicion_estado). No es una contradicción de semántica, es una acumulación de completitud pendiente: el marco debe extender su CHECK con estos 9 tipos adicionales antes de que cualquier implementación de este motor pueda escribir en esa tabla. Se registra también en el informe final de este handbook.

Invariantes de datos

  • ID-1: un Evento de decisión es inmutable una vez escrito — correcciones se hacen con un nuevo evento compensatorio, nunca editando el original (consistente con P3 del Architecture Handbook).
  • ID-2: la Prescripción vigente de un Slot es reemplazada atómicamente junto con su Evento correspondiente, en la misma transacción — nunca queda un estado donde el evento exista sin la prescripción actualizada o viceversa.
  • ID-3: el estado de estancamiento de un Slot es reconstruible completamente a partir de sus Eventos — no requiere una tabla de estado adicional si el replay (14) puede derivarlo, aunque una tabla de estado cacheada es una optimización válida de implementación.

Relación con el esquema existente

Este motor reutiliza profiles, workouts y workout_logs tal como los define el Architecture Handbook (10) — no introduce tablas de usuario nuevas. La única extensión de esquema que este documento exige es la del CHECK de progression_events señalada arriba.
