Backend Architecture

BREY no tiene un servidor separado — el "backend" son Server Actions y Route Handlers de Next.js corriendo sobre la infraestructura de Vercel, con Supabase como única base de datos y proveedor de auth.

Diagrama de capas del backend

Las piezas del backend

BE-01implementado

Server Actions

Responsabilidad
Punto de entrada de toda mutación desde el cliente — reciben el input (de un <form action={fn}> o invocación directa), validan, invocan repositorios
Ejemplo real
signOut() (lib/supabase/actions.ts) — "use server", invocada como <form action={signOut}> nativo de React 19, sin JS de cliente adicional
Regla
Una Server Action nunca contiene SQL directo — siempre delega en un repositorio (BE-03)
Dependencias permitidas
lib/supabase/server.ts, repositorios, validadores de dominio (lib/perfil/perfil.ts)
BE-02futuro

Application Services

Estado actual
No existe como capa distinta — las Server Actions de hoy son suficientemente simples (un repositorio, poca orquestación) para no necesitar un servicio de aplicación intermedio
Umbral de creación
Cuando un caso de uso orqueste ≥2 repositorios con lógica de coordinación no trivial — el primer candidato real es GenerarReporte del BCS Handbook (04), que combina Cliente + Mediciones + cálculo de interpretación
Responsabilidad especificada
Orquestar múltiples repositorios y/o motores de dominio para un caso de uso — sin contener SQL ni JSX
Relación con los motores
Un Application Service invoca un motor de dominio (BE-05) como función pura y persiste su resultado vía repositorio — nunca al revés
BE-03implementado

Repositories

Responsabilidad
Único punto de acceso de lectura/escritura a una tabla o agregado — recibe el SupabaseClient como primer parámetro (FT-10)
Ejemplo real
getProfile, getOrCreateProfile, updateProfile (lib/profile/repository.ts) — cada uno recibe supabase explícito
Regla
Un repositorio hace select("*") por defecto, no listas parciales de columnas — elimina duplicación de column-lists entre call sites (decisión de Sprint 4.1, documentada como trade-off aceptado)
Excepción documentada
components/layout/Navbar.tsx sigue con su propio .select("nombre") — corre client-side en cada página del sitio marketing (no solo /app), y forzarlo a traer el perfil completo (incluye lesiones/observaciones) solo para un nombre es un costo real y evitable en la ruta más caliente del sitio
BE-04implementado

Policies

Responsabilidad
Autorización a nivel de fila — vive en Postgres (RLS), no en TypeScript (08)
Regla
Ningún repositorio implementa su propio chequeo de "¿es este el dueño de la fila?" en código de aplicación — esa lógica vive exclusivamente en las políticas RLS de la tabla (05, 08); duplicarla en TypeScript sería una segunda fuente de verdad (FT-01)
BE-05implementado

Domain Services (motores)

Responsabilidad
Lógica de negocio pura, determinista, sin I/O (FT-03) — el "Domain" de la capa (02)
Ejemplo real
lib/diagnostico/motor.ts — recibe respuestas, devuelve un resultado, sin tocar Supabase
Especificados, no implementados
Motor BPS, Progression Engine (sus propios handbooks especifican el motor completo; aquí solo se fija que, cuando se construyan, deben seguir este mismo patrón de función pura)
Regla
Un motor nunca importa lib/supabase/* — si necesita datos, los recibe como parámetro ya resueltos por la Application Service/Server Action que lo invoca
BE-06implementado

Infrastructure

Responsabilidad
Adaptadores hacia sistemas externos — hoy, exclusivamente Supabase
Ejemplo real
lib/supabase/server.ts (cliente para Server Components/Actions), lib/supabase/client.ts (cliente para Client Components), lib/supabase/proxy.ts (refresco de sesión, 08)
BE-07futuro

Storage

Estado actual
Ningún módulo de hoy sube archivos — Supabase Storage no está configurado aún
Primer consumidor previsto
Fotografías de progreso del BCS Handbook (03, 11) — bucket separado, acceso solo vía referencia autenticada o token de EnlacePúblico, nunca URL directa (BCS Handbook, 11)
BE-08futuro

Events

Estado actual
Cero tablas de eventos en producción hoy — ver 07 para el contrato completo especificado por Motor BPS Handbook y Progression Engine Handbook, aún no implementado
BE-09futuro

Jobs y Schedulers

Estado actual
No existe ningún job en segundo plano ni cron configurado — el ciclo semanal del Motor BPS Handbook (batch, no reactivo, MBPS-ADR-04) requerirá esta pieza cuando se implemente
Candidato técnico
Vercel Cron Jobs (ya disponible en la plataforma de despliegue actual, 12) o Supabase Edge Functions con pg_cron — decisión pendiente, ver 15
