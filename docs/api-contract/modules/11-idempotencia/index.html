Idempotencia

Qué endpoints toleran un reintento de red sin duplicar efectos, con qué clave, y dónde el ecosistema todavía no tiene una respuesta — documentado como gap, no inventado.

Idempotentes por definición del método

Todo GET del catálogo (07) es idempotente por construcción — leer dos veces nunca cambia el resultado ni produce un efecto secundario de dominio. Todo PATCH con el mismo body produce el mismo estado final, salvo PATCH /bcs/mediciones/{id}, que crea una fila nueva en cada invocación exitosa por diseño (anula + crea, 07) — repetir la misma corrección dos veces crea dos Mediciones nuevas sucesivas, cada una anulando a la anterior; esto es coherente con el modelo de historial inmutable (IN-D1), no una falla de idempotencia.

Casos límite

  • Dos compras del mismo Usuario para Sistemas distintos, en ventana corta: la de timestamp anterior gana; la segunda se registra comercialmente pero no reactiva, y dispara anomalia para resolución humana (Motor BPS Handbook, 06).
  • Compra y Diagnóstico llegando en el mismo instante: la compra se procesa primero (crea el estado de espera), el Diagnóstico la resuelve después — commutativo solo para este par (Motor BPS Handbook, 06).
  • Dos dispositivos offline iniciando la misma sesión de Workout Player: al sincronizar, el timestamp de inicio más temprano gana; los eventos del perdedor se archivan como sesion_duplicada, visibles pero nunca contados en adherencia (Architecture Handbook, 09).
