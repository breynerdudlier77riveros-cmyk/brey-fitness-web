M1 — Endurecimiento RLS de workouts/workout_logs

implementado — Sprint 0
OrigenArchitecture Handbook (10), reafirmado por Architecture Review (AR-018)
PrecondiciónNinguna — es la primera migración, corrige una brecha ya identificada, no depende de nada nuevo
Cambioworkout_logs → solo select+insert propios; workouts → select+insert+update propio; delete desaparece de ambas — aplicado en supabase/schema.sql y supabase/migration_rls_endurecimiento.sql
PostcondiciónNingún usuario puede borrar su propio historial de entrenamientos — verificado contra el archivo real (Sprint 0)
RollbackRevertir a las políticas "CRUD propio" originales — documentado como posible pero desaconsejado, ya que reintroduce la brecha de seguridad que esta migración corrige

M2 — Tabla progression_events
OrigenArchitecture Handbook (10, tabla REQUERIDA) + Engineering Handbook (07, consolidación de 25 valores de tipo)
PrecondiciónM1 aplicada (no depende de M1 técnicamente, pero el orden de esta lista es también el orden de prioridad de riesgo — seguridad antes que funcionalidad nueva, Regla 5 de 01)
CambioCrea la tabla con columnas id, user_id, tipo, origen, razones, contexto, workout_log_id, created_at — el CHECK de tipo incluye los 25 valores consolidados desde el primer CREATE TABLE, no solo los 14 originales
PostcondiciónMotor BPS y Progression Engine pueden persistir decisiones; RLS: select+insert propios, sin update/delete (append-only, FT-09)
RollbackDROP TABLE — segura mientras no tenga datos reales; una vez en producción, requiere migración de exportación previa
