Anonimización

Sin estrategia de anonimización — el único mecanismo real es el acceso sin identidad

Ningún handbook especifica anonimización de datos en reposo (ej. hashear nombre para analítica agregada). El único mecanismo real relacionado es que el acceso vía bcs_enlaces_publicos se audita "sin identidad" — se registra que un enlace fue visitado, nunca quién lo visitó (BCS Handbook, 08; 14 de este documento) — pero eso es anonimizar el acceso, no el dato. No se inventa una estrategia de anonimización de datos aquí.

Retención

Sin política de retención — gap real, no se inventa aquí

Ningún handbook define cuánto tiempo se conserva un workout_log, un progression_event o una bcs_medicion antes de poder eliminarse por antigüedad. Todo el historial se conserva indefinidamente por diseño de auditoría (P3) — lo cual es una política implícita ("retención indefinida"), pero ningún documento la declara explícitamente como decisión de producto ni contempla un derecho de portabilidad/olvido más allá de la eliminación total de cuenta (abajo). Se registra como pregunta abierta (16).

Hard delete

CasoMecanismoAlcance
Eliminación de cuenta de UsuarioDELETE físico en auth.users, cascade realprofiles, diagnoses, workouts, workout_logs, progression_events — la única excepción reconocida a la inmutabilidad de historial (P3), por ser un derecho legal (Architecture Handbook, 10)
Eliminación permanente de Cliente (UC-04)DELETE físico en bcs_clientes, distinto del archivado reversibleCascada de revocación (no DELETE físico) de sus bcs_enlaces_publicos — las bcs_mediciones asociadas: comportamiento no especificado explícitamente por ningún handbook, ver 16
Gap — ¿qué pasa con las Mediciones de un Cliente eliminado permanentemente?

Ni el BCS Handbook ni el Implementation Handbook especifican si DELETE FROM bcs_clientes cascada un DELETE físico de sus bcs_mediciones, o si estas se conservan huérfanas para retención/auditoría legal. No se inventa una respuesta aquí — se registra como pregunta abierta (16).

Backup y restore

Sin política propia — gestión delegada a la infraestructura, sin decisión explícita de ningún handbook

Ningún handbook de BREY (incluido el Engineering Handbook) especifica una política de backup/restore propia — la expectativa implícita es que Supabase gestiona backups de la plataforma, pero ningún documento compromete una frecuencia, retención de backups, ni un procedimiento de restore probado. Este documento no inventa esa política — la registra como ausencia real (16).
