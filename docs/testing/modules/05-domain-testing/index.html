Domain Testing

No es lo mismo que Engine Testing (06): aquí se prueban las reglas estáticas del dominio — ownership, fronteras de contexto, invariantes — no el algoritmo de decisión de un motor específico.

Domain Testing vs. Engine Testing

Domain Testing (05)Engine Testing (06)
Pregunta que responde¿Esta estructura de datos/relación es válida según el dominio?¿Este motor decide lo correcto dado este historial?
Ejemplo¿bcs_mediciones.cliente_id puede ser nulo? (No — IN-D5)¿Progression Engine decide "avanza" con esta ventana? (PE-XXX)
Nivel típicounit sobre validadores, integration sobre constraints realesunit sobre el motor puro

Pruebas de frontera de bounded context

Cada prueba de frontera intenta cruzar una línea prohibida y espera que falle
flowchart LR
  T1["Test: BCS lee profiles"] -->|"debe fallar"| X1["✕ prohibido (BCS Handbook, 00)"]
  T2["Test: Core Training lee bcs_clientes"] -->|"debe fallar"| X2["✕ prohibido (Database Handbook, 02)"]
  T3["Test: Progression Engine consulta Recovery directamente"] -->|"debe fallar"| X3["✕ prohibido — solo recibe el Veredicto ya resuelto"]
  T4["Test: UI invoca evaluarProgresion directamente"] -->|"debe fallar"| X4["✕ violación de capas (Architecture Handbook, 11)"]

Estas cuatro pruebas no verifican lógica de negocio — verifican que la arquitectura sigue siendo la especificada. Se ejecutan como pruebas de integration contra el código real de acceso a datos, buscando cualquier ruta que las viole.
