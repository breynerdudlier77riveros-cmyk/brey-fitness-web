API Handbook

BREY no expone una API pública versionada — sus contratos internos son las firmas de los repositorios (Queries), las Server Actions (Commands) y los 2 Route Handlers reales. Este módulo formaliza esos contratos.

Regla: DTO de lectura ≠ DTO de escritura

Un DTO que sale de un repositorio (Profile) nunca es el mismo tipo que entra a una actualización (ProfileUpdateInput) — el de escritura es siempre un subconjunto parcial, sin campos gestionados por el sistema (id, created_at). Confirmado por el código real: ProfileUpdateInput es un tipo separado, no Partial<Profile> genérico.

Commands y Queries

TipoForma realEjemplo
QueryFunción async de un repositorio que solo lee, nombrada get<Entidad>getProfile(supabase, userId)
CommandServer Action o función de repositorio que muta, nombrada <verbo><Entidad>updateProfile(supabase, userId, patch), signOut()

Ninguna función mezcla ambas responsabilidades — una Query nunca tiene efectos secundarios, salvo el caso explícito de getOrCreateProfile (documentado en su propio nombre: "Get-or-Create" declara la escritura condicional desde la firma, no la esconde).

Responses

Convención real de los Route Handlers

Los 2 Route Handlers existentes (app/api/lead, app/api/contacto) devuelven siempre { ok: boolean, error?: string } — nunca solo un código HTTP sin cuerpo. error es un código corto en snake_case (invalid_email, not_configured, provider_error), no un mensaje de usuario final ni un stack trace. El código HTTP sí es significativo (400 input inválido, 503 configuración faltante, 502 proveedor externo falló) — ambos (código HTTP + error) se especifican siempre juntos, nunca uno sin el otro.

Los repositorios (fuera de Route Handlers) siguen una convención distinta pero igualmente consistente: null en caso de error o ausencia (FT-05, Fail Visible — nunca lanzan una excepción no capturada hacia el Server Component que los invoca).

Versionado

futuro — no existe hoy ningún esquema de versión en las rutas internas (no hay /api/v1/). Es aceptable porque estos endpoints son consumidos exclusivamente por el propio frontend de BREY, desplegado atómicamente junto al backend (12) — no hay un tercero consumiendo esta API que requiera coexistencia de versiones. Si BREY expone una API pública en el futuro (Coach IA con integraciones externas, por ejemplo), este documento exige introducir versionado desde el primer endpoint público, no retroactivamente.

Paginación, Filtros, Sorting

futuro — ningún repositorio actual pagina (el volumen de datos por usuario hoy no lo requiere: un usuario tiene, como máximo, cientos de workout_logs). El BCS Handbook (12) ya especifica el patrón para cuando se implemente: paginación por rango de fechas antes que OFFSET/LIMIT genérico, porque el caso de uso real siempre es "ver el historial reciente", no "saltar a la página 7".

Idempotencia

Ejemplo real: app/api/lead trata una respuesta duplicate_parameter de Brevo como éxito ({ ok: true }), no como error — registrar el mismo email dos veces no debe fallar visiblemente para el usuario que reenvía un formulario (FT-04).

Timeouts y Retry

futuro — el fetch() a Brevo en app/api/lead no tiene timeout explícito ni política de reintento; depende del timeout por defecto de la plataforma de despliegue (12). Se documenta como deuda técnica (15): cualquier integración externa nueva debe declarar su propio timeout explícito desde el diseño, no heredar el default silenciosamente.

Eventos

Ningún Command actual emite un evento de dominio persistido — ver 07 para el contrato completo ya especificado por los handbooks de motor, pendiente de implementación.
