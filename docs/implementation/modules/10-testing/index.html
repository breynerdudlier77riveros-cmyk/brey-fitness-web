Testing

El Engineering Handbook (10) ya fija la estrategia (Unit → Integration → E2E, motores como funciones puras testeables sin mocks). Este módulo fija cuándo, exactamente, se escribe cada nivel en relación con el orden de construcción de 04.

Orden exacto de testing

MomentoQué se pruebaNivel
Inmediatamente tras M1 (05)Que DELETE sobre workouts/workout_logs es rechazado por RLSIntegration
Inmediatamente tras cada repositorio nuevo (06)Forma exacta del DTO devuelto, manejo de ausencia (null, FT-05)Unit (con Supabase real de test, no mock — Engineering Handbook 10)
Inmediatamente tras el pipeline base de Progression Engine (08)El pipeline sin reglas siempre produce "sostiene" — comportamiento base antes de añadir lógicaUnit
Tras cada grupo de reglas añadido (08 — micro, macro, autorregulación, estancamiento, deload)Los casos límite ya documentados en el propio catálogo (Progression Engine Handbook, 07 — "ejemplo inválido" de cada regla)Unit
Tras completar la máquina de estados de Motor BPS (08)Las 15 transiciones, con foco en las que la Architecture Review marcó como casos límite (T11 auto-pausa, T13 retroceso propuesto)Unit
Tras el paso 14 de 04 (Integración)Los 5 casos del checklist de integración (09)Integration
Tras el paso 15 de 04 (primer ciclo E2E)El flujo completo de un usuario real desde registro hasta primera semana generadaE2E — el único punto del roadmap donde se justifica, según la propia prioridad del Engineering Handbook (10: E2E es "el más costoso de mantener, se introduce último")

Orden de construcción de factories/fixtures

Antes que el primer test de cada dominio, no después: una factory de Profile/Workout para el Core Product ya debería existir (aunque no haya tests hoy — es deuda, Engineering Handbook 10); las factories de Cliente/Medición del BCS y de Decision/Veredicto de los motores se crean en el mismo paso que su primer repositorio o pipeline, nunca como una tarea separada "para después".

La lista roja del Engineering Handbook, aplicada a este roadmap

Los tres invariantes que "nunca deben romperse" (Engineering Handbook, 10) se verifican en los siguientes puntos exactos de este roadmap:

  • Inmutabilidad de historial — verificada en el primer punto de la tabla de arriba (tras M1), antes de cualquier otra prueba.
  • RLS activo en toda tabla nueva — verificado inmediatamente después de cada migración (M2, M3), antes de escribir el primer repositorio que la use.
  • Ningún secreto con prefijo NEXT_PUBLIC_ — verificado en el checklist de Seguridad de cada Pull Request (13), no como una prueba automatizada separada mientras no exista CI (Engineering Handbook, 12).
