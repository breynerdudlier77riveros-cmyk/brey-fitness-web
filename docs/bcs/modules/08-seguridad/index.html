Módulo 08 · Acceso y datos sensibles

Seguridad

Permisos, seguridad a nivel de fila (RLS) y auditoría — quién puede tocar qué, y cómo queda registrado cada cambio. Este módulo también cumple la promesa de detalle de observabilidad hecha en 01.

IdentidadAutenticaciónPermisos
EntrenadorLogin autenticado (reutiliza el mecanismo del Core Product, 01)Lectura y escritura total sobre sus propios Clientes, Mediciones y EnlacesPúblicos
Cliente (vía enlace público)Ninguna — posesión del token es la única credencial (09, 10)Lectura exclusiva del Reporte de un único Cliente — cero acceso a cualquier otro dato del sistema
Cualquier otra identidadn/aSin acceso — no existe un rol "administrador global" distinto del propio entrenador en v1 (single-tenant, 12, 16)

Seguridad a nivel de fila (RLS)

Tabla conceptualPolítica
ClienteSolo visible/editable por el entrenador propietario — en v1 con un único entrenador, la política es trivial, pero se especifica como si existieran varios para no bloquear 12/17
MediciónSolo visible/editable por el entrenador propietario del Cliente al que pertenece; visible en modo exclusivamente lectura para quien presente el token del EnlacePúblico correspondiente a ese mismo Cliente
EnlacePúblicoCreación/revocación solo por el entrenador propietario; resolución de token→reporte es la única operación que un actor anónimo puede ejecutar, y solo si el token está en estado activo (02)
FotografíaMismas reglas que Medición — nunca accesible fuera del contexto de su Cliente (11)

Auditoría

Toda operación de escritura queda registrada de forma inmutable: quién (el entrenador — identidad única en v1, pero el campo existe para 12), qué acción, sobre qué entidad, cuándo, y el valor anterior cuando aplique (para Mediciones corregidas, 05).

Acción auditadaQué se registra
Crear/editar/archivar/eliminar ClienteIdentidad del entrenador, timestamp, estado anterior y nuevo
Registrar/corregir MediciónIdentidad del entrenador, timestamp, Medición anulada (si aplica) referenciada por id
Crear/revocar EnlacePúblicoIdentidad del entrenador, timestamp, token afectado (nunca el token en texto plano en el log de auditoría — solo su identificador interno)
Acceso vía EnlacePúblicoTimestamp del acceso — sin identidad, porque el acceso es anónimo por diseño (09, 10); se audita el hecho de "el enlace X fue visitado", no quién lo visitó

Casos límite

CasoComportamiento
Múltiples intentos de token inválido en poco tiempo desde el mismo origenSe registra el patrón como token_invalido_intentado repetido — mitigación de fuerza bruta (rate limiting) es responsabilidad de infraestructura, no de este dominio, pero el evento debe existir para que esa capa pueda actuar (13, 17)
Entrenador intenta acceder a un Cliente que no le pertenece (futuro multi-entrenador, 12)Acceso denegado — no existe en v1 con un solo entrenador, pero la política de RLS se especifica ya pensando en ese caso
