Módulo 13 · Checklists y gobernanza

Release Checklist

Ocho checklists. Cada ítem cita el módulo/handbook que lo exige — ninguno es una preferencia nueva de este documento.

Checklist de Pull Request
  • El código sigue las convenciones de naming reales (Engineering Handbook, 13) — interface para Props/formas de objeto, type para uniones.
  • Todo comentario explica el por qué, nunca el qué (13).
  • Ningún repositorio nuevo hace select parcial de columnas sin justificación documentada (04, BE-03).
  • Ningún secreto de servidor con prefijo NEXT_PUBLIC_ (08).
  • Si toca una tabla, RLS fue verificado activo manualmente (05, 08) — no hay CI que lo haga automáticamente todavía.
Checklist de Merge
  • El PR pasó su propio checklist completo (arriba).
  • npm run lint sin errores (Engineering Handbook, 13).
  • npm run build exitoso.
  • Si la rama incluye una migración, el orden respecto a otras migraciones pendientes está confirmado (05).
  • El estado de la pieza correspondiente en 12 se actualiza como parte del mismo PR, no en un paso separado.
Checklist antes de producción
  • Toda migración de esta release fue aplicada primero en Preview, no directo en producción (Engineering Handbook, 12).
  • Si Preview y Producción comparten proyecto de Supabase (riesgo real, Architecture Review AR-022), se confirma explícitamente que ningún dato de prueba puede confundirse con datos reales.
  • Las variables de entorno nuevas están documentadas en .env.example antes de configurarse en el entorno real (Engineering Handbook, 12).
  • Ningún hallazgo 🔴 de la Architecture Review que afecte a esta release sigue abierto sin un IMP-ADR que lo resuelva (14).
Checklist de Release
  • El estado de todas las piezas incluidas en la release está en verificado en la tabla de 12, no solo implementado.
  • El Roadmap (03) refleja la fase real alcanzada tras esta release.
  • Ningún checklist de esta lista de 8 quedó parcialmente completado.
Checklist de Testing
  • Todo motor nuevo tiene cobertura de sus casos límite ya documentados en su propio handbook (10, Engineering Handbook).
  • Todo repositorio nuevo tiene al menos un test de Integration contra Supabase real, nunca mockeado (Engineering Handbook, 10).
  • Si el test depende del Veredicto de Recovery, usa la forma canónica de IMP-ADR-01, no una de las dos formas divergentes originales (Architecture Review AR-025).
  • La "lista roja" de invariantes (inmutabilidad de historial, RLS activo, secretos) fue verificada para este cambio específico (10 de este handbook).
Checklist de Seguridad
  • RLS activo y verificado manualmente en cualquier tabla tocada (05, 08 del Engineering Handbook).
  • Ningún token nuevo tiene menos de 21 caracteres aleatorios si sirve como credencial de acceso sin autenticación (BCS Handbook, 10; BCS-ADR-02).
  • Ningún log incluye un secreto o un token de EnlacePúblico en texto plano (BCS Handbook, 08).
  • SUPABASE_SERVICE_ROLE_KEY sigue sin usarse, o si se activa, se verificó manualmente que no aparece en ningún archivo alcanzable por el cliente (Architecture Review AR-019).
Checklist de Performance
  • Ningún repositorio nuevo introduce una consulta dentro de un bucle (N+1) (Engineering Handbook, 09).
  • Ninguna memoización (useMemo/useCallback) se añade sin un problema de rendimiento medido primero (09, Engineering Handbook).
  • Si la feature toca el Reporte del BCS, se confirma que el riesgo de recomputación creciente (Architecture Review AR-021) sigue siendo aceptable al volumen actual de datos, o se implementa cache antes de continuar.
Checklist de Accesibilidad
  • Todo elemento interactivo nuevo tiene un área táctil mínima de 44×44px (BCS Design System Handbook, 15).
  • Ninguna información se comunica solo por color — siempre ícono o texto acompañante (15).
  • Todo gráfico nuevo tiene una alternativa tabular accesible (15).
  • El contraste de cualquier texto nuevo cumple el mínimo ya verificado en la matriz de contraste (15).
