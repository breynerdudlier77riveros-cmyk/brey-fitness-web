Testing Handbook

Cero infraestructura de testing existe hoy — sin Jest, Vitest, Playwright ni Testing Library en package.json. Este módulo no finge lo contrario: especifica la estrategia exacta para cuando se introduzca, aprovechando que el dominio ya se diseñó para ser testeable (FT-08) desde antes de tener un test runner.

Estado real, sin excepciones

Verificado contra package.json: 0 dependencias de testing, 0 archivos *.test.ts/*.spec.ts en el repositorio. Cualquier afirmación de cobertura de este módulo es una especificación de objetivo, nunca una medición actual.

Por qué el dominio ya es testeable sin test runner

FT-08 (Testabilidad) y FT-03 (Determinismo) ya obligan a que los motores de dominio (lib/diagnostico/motor.ts, y los futuros Motor BPS/Progression Engine) sean funciones puras — sin import de Supabase, sin Date.now() implícito. Esto significa que, el día que se instale un test runner, la mayoría de la lógica crítica de BREY ya es testeable sin mocks de base de datos: entrada in, salida out. Decisión formal en ENG-ADR-06 (14).

Los tres niveles

NivelQué cubrePrioridad de introducción
UnitMotores de dominio puros (lib/diagnostico/motor.ts, futuros Motor BPS/Progression Engine), funciones de validación (validarPerfil), parsers (numOrNull)1 — máximo valor, mínimo esfuerzo (sin mocks)
IntegrationRepositorios contra una base de datos Supabase de test real (no mockeada — un mock de Supabase divergería de RLS real)2
E2EFlujos completos de usuario (registro → perfil → primer entrenamiento)3 — el más costoso de mantener, se introduce último

Factories, Fixtures y Mocks

ConceptoRegla especificada
FactoriesUna función build<Entidad>(overrides?) por DTO de dominio (06) — nunca un objeto literal repetido en cada test
FixturesDatos de referencia estables (ej. las respuestas completas de un Diagnóstico que produce un resultado conocido) — versionados junto al test, nunca generados aleatoriamente
MocksNunca se mockea Supabase completo para tests de Integration (arriba) — se mockea solo en tests de Unit que prueban una Server Action de forma aislada, y siempre mediante inyección del SupabaseClient como parámetro (FT-10 ya lo permite sin trabajo adicional)

Cobertura

Sin objetivo numérico de cobertura global — un 100% en lib/utils.ts vale menos que un 60% bien dirigido a los motores de decisión. Regla: todo motor de dominio nuevo (Motor BPS, Progression Engine cuando se implementen) requiere cobertura de sus casos límite documentados en su propio handbook (ej. Motor BPS Handbook 10, Progression Engine Handbook cada regla PE-XXX con "ejemplo inválido") antes de considerarse listo para producción — esa lista de casos límite ya escrita es, en la práctica, el plan de pruebas.

Casos críticos que nunca deben romperse

  • La coerción numérica de numOrNull() — un regreso silencioso al bug de concatenación de strings (Sprint 4.1) es el ejemplo canónico de qué probar primero.
  • Idempotencia de handle_new_user() — un usuario nuevo nunca debe fallar su registro por una carrera de triggers.
  • Cualquier CHECK de rango físico (05) debe tener su contraparte de test en la validación de TypeScript — ambas capas deben rechazar exactamente los mismos valores inválidos, nunca divergir.

Casos borde obligatorios

Todo motor de dominio prueba explícitamente: entrada vacía/mínima, valores en el límite exacto de un CHECK, y el caso de "ventana insuficiente" (P6/FT-05, Fail Visible) — un motor que no declara cómo se comporta sin datos suficientes no está listo para su primer test, mucho menos para producción.

Los tres invariantes que ningún cambio de código puede violar, con o sin tests

(1) Ninguna Medición/Log histórico se edita en sitio (FT-09, Inmutabilidad) — cualquier PR que haga un UPDATE directo sobre una fila de historial debe rechazarse en revisión, con o sin test que lo cubra. (2) RLS activo en toda tabla nueva (08) — verificación manual obligatoria hasta que exista un test de integración automatizado que lo confirme. (3) Ningún secreto de servidor con prefijo NEXT_PUBLIC_ (08).
