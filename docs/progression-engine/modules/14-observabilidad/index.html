Módulo 14 · Sistema

Observabilidad

Qué se registra, con qué nivel, qué métricas y KPIs se derivan, cómo se audita el comportamiento del motor en producción, y cómo se reconstruye ("replay") una decisión pasada.

Objetivo

Que ninguna decisión del motor sea una caja negra meses después de tomada — P2 (explicabilidad) aplicado operativamente.

Niveles de registro

NivelCuándo se emiteEjemplo

WarningSituaciones válidas pero atípicas — no bloquean el pipelineVentana con más de un hueco reciente; deload preventivo sugerido 2 veces seguidas para el mismo Slot
ErrorEntradas inválidas que abortan el pipeline (paso 2, 06)PRESCRIPCION_INCOHERENTE, JERARQUIA_INCONSISTENTE

Qué trae cada evento (contrato mínimo)

Todo evento emitido por este motor incluye, sin excepción: tipo, Slot afectado, valores de entrada relevantes al momento de la decisión, valores de salida, razón en lenguaje explícito (no solo un código), regla(s) PE-XXX que lo originaron, y fecha del ciclo. Esto es lo que permite el replay.

Auditorías

Toda regla PE-XXX debe ser trazable desde un evento hasta su definición exacta en 07 — la matriz Regla→Pipeline (06) y las matrices de este documento existen precisamente para que una auditoría externa pueda recorrer el camino completo: evento → paso del pipeline → regla → nivel de evidencia, sin intervención humana adicional.

Replay

Dado el determinismo (P1/IN-P1), reprocesar las mismas 5 entradas de un ciclo pasado con la misma versión del catálogo de reglas debe producir exactamente la misma Decisión. El replay es la herramienta de diagnóstico principal ante un reporte de "decisión rara": se reconstruyen las 5 entradas tal como existían en ese momento (nunca con datos actuales) y se re-ejecuta el pipeline en un entorno de auditoría.

Matriz Error → Recuperación

ErrorRecuperación
Veredicto de Recovery ausenteEl orquestador reintenta la consulta a Recovery antes de invocar este motor — este motor nunca sustituye un veredicto ausente por un default
Ventana desordenadaEl repositorio de origen corrige el orden y reintenta — el motor nunca ordena por su cuenta (evitaría enmascarar un bug real upstream)
PRESCRIPCION_INCOHERENTESe usa el default de cadena como Prescripción base y se registra la anomalía para revisión — el ciclo no se pierde, se degrada de forma segura
SISTEMA_ESFUERZO_MIXTOBloquea la invocación — requiere corrección en el origen del programa (Training Framework), no tiene fallback seguro automatizable
JERARQUIA_INCONSISTENTEBloquea la invocación — requiere reconciliación manual del puntero, análoga a la reparación de "estados imposibles" del Motor BPS Handbook (05)
ESTADO_ESTANCAMIENTO_INCONSISTENTEEl Slot se trata como recién detectado (contador en 0) — recuperación optimista, prioriza continuidad de servicio sobre exactitud retroactiva del contador
PRESCRIPCION_PREVIA_AUSENTE (post-deload)Fallback al default de cadena, se registra la anomalía — nunca bloquea la reincorporación
